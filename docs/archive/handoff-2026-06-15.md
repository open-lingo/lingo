## Why this matters (the problem we were really solving)

A new learner picks JA and the **flashcard reviewer was dead** for them: it
only played backend *subscription* decks, so a course-only user hit a
"subscribe to a deck" empty state. Meanwhile the curriculum's own review
machinery had a latent scheduling bug. The session turned into a deep design
pass on **how/when atoms enter and move through FSRS** — and produced a spec
that supersedes the prior retention doc's intake decisions.

## The journey (decisions, in order — important context)

1. **FTUE P1 "first review after lesson 1"** was the starting ask — but it
   was premised on the reviewer being usable. It wasn't.
2. **Reviewer didn't include the course deck.** `useSubscriptionQueue` reads
   only backend subscriptions; the client-generated course deck (`courseDeck.ts`,
   id `ja-course`, `courseId: "mock-1"`) never entered. **Phase 1** injects it.
3. **Seed-on-load bug.** Loading the reviewer seeded the SRS store for *every*
   unlocked atom due-**today** → flooded "Due: 8" and bypassed any throttle.
   Root cause (ralph-confirmed): `buildSrsReviewLesson` did `setCardState` at
   **build time**, and the course-deck **sentence-miner builds every review
   lesson** to mine examples. Construction was mutating global state. → **D4**.
4. **Intake model resolved (Spencer).** No same-day review (bad memory test);
   default = *every unlocked word reviewable* (lesson pace is the throttle, not
   an Anki-style new-card cap); words become due **next day**. Research pass
   (inline) confirmed: Anki's new-card cap substitutes for *absent* external
   pacing — we *have* lesson pacing; review load ∝ new-card rate; first gap ≈
   overnight (Cepeda 2006). → **D5** + the spec, which **supersedes** the old
   retention doc's §4/D7/§8 ("do not seed-at-unlock", "adaptive cap").
5. **In-course review is structural** — review lessons (`ja-mN-review-1/2`,
   2 per content module) generated by `buildSrsReviewLesson`; grading each step
   is the FSRS write. **But they don't gate progression today**
   (`getModuleStatus` filters `isContentLesson`) → skippable. Spencer's intent:
   not skippable. → **D3** (needs hard-vs-soft).
6. **Ralph caught D2's false premise.** The "sub-lesson review tails write
   FSRS" lever assumed tails that **don't exist for vocab**:
   `augmentWithReviewTail`/`withKanaReviewTail` are **kana-only**, emit
   kana-glyph `symbol_recognition` with **no `exercisedAtoms`**. Dropping the
   `LessonPage:488` gate alone would instead grade *current-atom* (same-day)
   practice — wrong. → **D2 is generative work** (author a vocab prior-atom
   tail), not a one-liner.

## The model (D1–D8) — read the spec

`docs/srs-scheduling-model-2026-06-15.md` is the source of truth. One-paragraph:
> One unified FSRS schedule. Review woven through the course (sub-lesson
> prior-atom steps = primary write [D2], non-skippable review lessons [D3]).
> Course self-covers review at normal pace → standalone reviewer is a
> supplement (quest-driven), defaulting to all-due/no-cap [D5]. A word is
> reviewable the day **after** unlock [D4], never same-day. Kana scheduled but
> not surfaced; ages out ~M3.

Spec §7 lists open questions; §8 is the ralph punch-list + docs-to-reconcile.

## Remaining work + the decisions you owe

### D3 — gate review lessons (needs your call: **hard vs soft**)
`moduleProgress.ts:getModuleStatus` filters `isContentLesson`, so finishing a
module's *content* lessons marks it complete + unlocks the next **without** the
2 review lessons. You said reviews shouldn't be skippable. The fix is one
function — but **a hard wall before the next module could hurt momentum**
(spec §7.8). Decide: hard-gate (must finish reviews) vs soft (strong nudge,
e.g. the pulsing path already funnels via `getCurrentModuleIndex`, which counts
all lessons). Note: with D4, review lessons are never empty (the module's just-
unlocked atoms are `isNew` → always selected), so gating on them is sound.

### D2 — vocab prior-atom review tail (the "main piece", real work)
Author a build-time generator (the vocab analogue of `kanaReviewTails`):
append prior-atom review steps — carrying `exercisedAtoms` on **prior** atoms —
to content sub-lessons, and change `LessonPage:488` from a **lesson-id** gate to
a **step-scoped** one (this step is a prior-atom review → write FSRS; keep
excluding current-atom same-day practice). Reuse `buildSrsReviewLesson`'s
step-builders (`audioImageMcq`, `vocabMcq`, `build`, …). **Verify** generated
tail steps point at prior atoms (else same-day grading). This is what makes
review scale with lessons (intake ≥ introduction; today ~10 new-to-SRS/module
via review lessons vs ~20–37 introduced — a latent deficit currently masked by
the now-removed seed bug).

## Gotchas for the next agent
- `rg -r` is a footgun (it means `--replace`); use `rg -n` / `rg -l`.
- The reviewer test isolation trick: an **unauthenticated** profile has no
  backend decks, so anything in the reviewer is provably the course-deck
  injection. Seed `lingo:unlocked-atoms` + clear `open-lingo-srs:v2` to set up.
- `createInitialState` is due-**today** — any "schedule for later" needs
  `createSeededState(dueDate)`.
- The M1 id landmine holds: `ja-m1-l1` is the *vowels* lesson; review lessons
  live inside content modules (m3–m28), not separate review modules
  (`eyebrow:"Review"` count = 0; that code is dead).
