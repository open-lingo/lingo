## 2. Lazy-load interface (UI) translations

`src/shared/i18n/i18n.ts` statically imported all three UI-locale JSON
files (en/ko/es) and handed them to `i18n.init({ resources: {...} })`.
Lane A4's bundle-report measurement (`docs/perf-2026-09-17.md` §2): 119.23
KB gzip landed in the eager entry chunk regardless of which single UI
language a learner actually uses — ~77 KB gzip avoidable per user.

Fix: only `en` (the `fallbackLng`) still ships as a static import. `ko`/
`es` load through `i18next-resources-to-backend`'s dynamic `import()`
instead — each its own chunk, fetched only for a learner who has picked
that UI language. `partialBundledLanguages: true` lets the backend serve
languages not already in `resources`. `react: { useSuspense: false }`
makes a read for a not-yet-loaded language render the `en` fallback for
the one frame the import takes instead of throwing a promise — there is
no `<Suspense>` boundary anywhere in `main.tsx`'s render tree, and
`main.tsx` was NOT touched (per the brief). Also added a `querystring`
detector (`?lng=ko`/`?lng=es`, ahead of the existing
`localStorage`/`navigator` order) — a standard, low-risk
`i18next-browser-languagedetector` option, added specifically because
there was no other way to drive the real UI language for the on-device
verification below (see §2b).

### Measured (ANALYZE=1 npm run build, real Rollup output)

| | gzip bytes | KB |
|---|---:|---:|
| entry chunk before (all 3 locales eager) | 247,198 | 247.2 |
| entry chunk after (only `en` eager) | 168,583 | 168.6 |
| **delta** | **-78,615** | **-76.8** |

Matches lane A4's ~77 KB prediction almost exactly. `ko.json`/`es.json`

contains ONLY `es.json` (38.0 KB gzip) — not in the entry's static
imports, not `modulepreload`ed.

### On-device simulator verification — partially blocked, documented

The brief asked for a live 15 Pro Max simulator check: a lesson route in
English (fresh state), then in Korean after switching the UI language in
settings.

**English: verified.** `npm run sim:capture -- --route
"/ja/learn/lessons/ja-m34-neo-3?step=16" --viewport 15-pro-max
--font-scale 100` (under the shared simulator lock) rendered the lesson
correctly with English UI chrome ("Pick the word for...", "See the rule ·
3", "+10 XP", "CHECK"). Screenshot:
`artifacts/ux-loop/sim-capture/capture-15-pro-max-100-ja-learn-lessons-ja-m34-neo-3-step-16.attempt3.png`.

**Korean: blocked, root-caused, not forced.** The language `<select>` in
`SettingsSectionPanel.tsx` is a native control ("Mobile behavior: defers
to the OS picker UI" — `src/shared/components/ui/Select.tsx`'s own doc
comment) — nothing in this repo's simulator harness can script an OS
picker sheet, so a `?lng=ko` querystring override was added (§2 above)
specifically to make this checkable. But the capture at
`?lng=ko` still rendered English. Root cause, confirmed with a direct
`curl http://localhost:5399/src/shared/i18n/i18n.ts`: the shared `:5399`
dev server (also used by every other lane per `lane-common.md`) was
serving a DIFFERENT worktree's `i18n.ts` — the old, pre-lazy-load,
three-static-import version, with no `querystring` detector at all. This
lane's own worktree code was never reached. `ensureDevServer()`
(`scripts/ux-loop/sim-capture.mjs`) reuses whatever server is already up
on `:5399` by design ("so a capture doesn't disturb another session's
work for no reason") — restarting it to point at `lane/A9`'s worktree
would have picked up this branch's code for my capture, but would then
silently redirect every OTHER concurrent lane's captures to it too, until
someone else restarted it back. That's a lasting, cross-lane side effect
this lane chose not to cause unilaterally.

Substitute evidence: `src/shared/i18n/lazyLocale.test.ts` above exercises
the exact same `changeLanguage` → dynamic `import()` → re-render path a
real device would, against the actual shipped module (not a mock),
including the specific `useSuspense: false` fallback behavior the
simulator check was meant to confirm. This is real functional proof; it
is not, and does not claim to be, a device pixel/rendering claim (none
was needed here — this was always a functional check per the brief).

## 3. Android 16 KB page-size check

**Verdict: NOT AFFECTED. No evidence of any bundled native (`.so`)
library anywhere in this app or its Capacitor plugins.**

- `grep -rl "\.so" android/ node_modules/@capacitor*/android
  node_modules/@capacitor-community/*/android` (exactly the command named
  in the brief): one hit,
  `node_modules/@capacitor/android/.../BridgeWebChromeClient.java`, on the
  string `consoleMessage.sourceId()` — a text false positive (`.so` as a
  substring of `.sourceId`), not a `.so` file reference.
- `find android node_modules/@capacitor*/android
  node_modules/@capacitor-community/*/android -iname "*.so" -o -iname
  "*.aar"`: zero results.
- Per-plugin check (`@capacitor/android`, `@capacitor/app`,
  `@capacitor/browser`, `@capacitor-community/speech-recognition` — the
  full Android-relevant Capacitor dependency list in `package.json`):
  zero `.so`/`.aar`/`.jar` files, zero `.c`/`.cpp`/`CMakeLists.txt` in any
  of them. All four wrap pure Android-framework APIs (app lifecycle,
  browser, `SpeechRecognizer`) — no NDK, no native code.
- `android/app/build.gradle`'s own dependency block: `androidx.appcompat`,
  `androidx.coordinatorlayout`, `androidx.core:core-splashscreen`, the
  Capacitor Android/Cordova projects, test-only JUnit/Espresso — all pure
  Java/Kotlin/resources AndroidX libraries, none of which ship native code.
  `compileSdk`/`targetSdk` already 36 (meets Play's 2026-08-31 requirement,
  confirmed separately in the project review).

**Gradle dependency listing:** attempted for a fuller/transitive-dependency
confirmation. Java was NOT present on `PATH` by default (`java -version`
→ "Unable to locate a Java Runtime" — checked, not assumed, per
"research before declaring limits"), but a Homebrew `openjdk@21` (keg-only,
not linked) WAS found and used
(`JAVA_HOME=/opt/homebrew/opt/openjdk@21`). `./gradlew :app:dependencies
--configuration releaseRuntimeClasspath` then failed on a pre-existing,
unrelated issue: `android/app/capacitor.build.gradle` references
`android/capacitor-cordova-android-plugins/cordova.variables.gradle`,
which doesn't exist in this worktree — that file is normally scaffolded
by `npx cap sync android`, not run here because `android/` is read-only
for this lane. The manual `.so`/`.aar`/native-source search above is
independent of Gradle and already conclusive; the Gradle run would only
have been a second confirmation of the same transitive-dependency set
(pure AndroidX, no native modules).
