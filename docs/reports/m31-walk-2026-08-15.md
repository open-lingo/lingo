## 1. Reactive grammar tip fired for a different mistake — COURSE-WIDE · FIXED

**Seen:** L1 build `こどもが すきだから えんぴつを あげる。` (`m31.ir.yaml:426`).
Spencer dropped the `だ` and got the Quick Fix card for
`✗ともだちに プレゼントを もらう。 / ✓ともだちに プレゼントを あげる。` — a
different sentence, and an error he had not made.

**Cause:** `tipFromRule` (`deriveGrammarMicroSteps.ts:33`) derives ONE tip per
grammar-rule card, from that card's `antiPattern` + `examples[0]`, and tags
every graded step in the card's drill span with it. The card is lesson-scoped
by construction.

A guard for exactly this already existed — `reactiveTipGate.ts`, written after
the m6 walk on 2026-07-23 ("we need to verify their actual error, this is
unhelpful"). It extracts the tip's characteristic mistake (the longest
whitespace chunk of `wrongJa` absent from `rightJa`) and only fires when the
learner's answer contains it. But its docstring exempted tile builds as unable
to supply answer text, and `LessonPage.tsx` fired the card whenever
`answerText === undefined`. So the m6 fix covered typed steps and left the
build class in exactly the state it was written to fix.

**Fix:** `BuildSentenceStepView.handleSubmit` now reports `placed.join(" ")` as
the answer text — the tray IS the produced sentence, and `normalizeTypedAnswer`
strips the join spaces. A dropped `だ` no longer contains `もらう`, so no card
fires. Gate docstring and the `LessonPage` comment corrected; MCQs remain the
only always-fire class (their answer is an option id, not a sentence).

Regression: `BuildSentenceLeniency.test.tsx` now asserts the reported answer
text, not just the verdict.

**Not fixed (deliberate):** the tip is still lesson-scoped, so when it DOES
fire it quotes the rule card's sentence rather than the one you missed, and
`ruleLine: step.rule` passes the entire rule paragraph — which is why the modal
is a wall of text. Both are authoring-surface changes across ~94 rule cards.
For the audit.

## 2. Cloze frames never show kanji — COURSE-WIDE · FIXED

**Seen:** L1 cloze `ははは せんせいに はなを ___。` rendered every word as kana
at module 31. Spencer: "do we never teach hana kanji … where is the one for
haha and sensei".

**Cause:** structural, not per-word. `ParticleClozeStep.prompt` was
`{ before: string; after: string }` — bare strings. `applyKanjiSurfaces`
rewrites per annotation segment, gated on `atomId`, and atomIds are attached by
the sentence factories. A cloze frame had no annotation to attach them to, so
the pass could never reach it. **Every cloze frame in the course rendered kana
at every module — 319 authored IR beats.**

**Fix:** `cloze()` now emits `beforeAnnotation` / `afterAnnotation` via
`buildSentenceAnnotation`, the identical treatment `conjugationCloze` already
had; `ParticleClozeStepView` renders them when present. No change to
`applyKanjiSurfaces` — the `*Annotation` key convention did the rest. Grading
and audio keys stay pure kana. Regression tests in
`applyKanjiSurfaces.test.ts`.

Verified: 母 and 先生 now substitute at m31.

### 2a. 花 can never auto-kanji-fy — OPEN, needs a ruling

はな resolves to TWO atoms — `hana` 花 (flower) and `hana-nose` 鼻 (nose), both
`fromModule: m1`. The surface pass refuses ambiguous homographs by design, so
花 will stay kana in every sentence no matter how many modules pass. The glyph
IS in the catalog (`n5Kanji.ts:692`, `introducedAtModule: 18`) but no module
drills it, so it is currently unreachable by either route.

先生 got taught the other way: two authored `kind: kanji` beats at
`m28.ir.yaml:719,747`, which author the surface directly and are
homograph-safe. That is the available fix for 花 — an authored beat, in
whichever module Spencer wants it. m31 currently ships four kanji beats
(友達 / 切符 / 家族 / お金); a fifth changes the module's shape, so this is his
call, not mine.

Worth checking in the audit: how many other catalog glyphs are unreachable the
same way (homograph-blocked from the pass AND undrilled by any beat).

## 3. Sentence-build tiles too small — FIXED

**Seen:** a 9-tile `build_sentence` bank rendered visibly smaller than the
same words on a `listening_build` tile. Spencer: "increase the element sizes
in the middle of screen to about same at listen build".

**Cause:** two size tiers only. `bigTiles = isWordBuild || tiles.length <= 6`,
so every 7+ tile sentence bank dropped to `text-base sm:text-lg` while
`listening_build` uses `text-2xl sm:text-3xl` unconditionally.

**Fix:** three tiers, and the bump is `sm:`-only. Tile size is not what
overflows the fixed shell — ROW COUNT is, and row count is set by container
WIDTH. Below 640px every tier is byte-identical to what shipped; from `sm:`
up the tiles take listening_build's size. 12+ tile banks get their own
`sm:text-xl` tier.

Measured on `ja-m31-neo-1`, stage `scrollHeight - clientHeight`, before →
after:

| step | tiles | 375×667 | 390×844 | 1280×700 | 1440×900 |
|---|---|---|---|---|---|
| 11 | 9 | 0 → 0 | 0 → 0 | 0 → 0 | 0 → 0 |
| 15 | 15 | 185 → 185 | 31 → 31 | 0 → 0 | 0 → 0 |

Zero regression at every viewport. (The 185px residual at 375×667 is
pre-existing B092-class debt. For reference `listening_build` itself — the
size being matched — measures **264px** of overflow at that viewport.)

Measured with the mobile gate's own trick: a dev server on a spare port with
`VITE_E2E=true VITE_DEV_AUTH_BYPASS=true`. `.auth/user.json` is expired, so
an authed lesson URL bounces to the marketing origin and any measurement
against :5173 silently measures the wrong site.

## 4. "So close" — one forgivable omission — SHIPPED

**Asked for:** "the 'so close' feature on these bigger sentences, where one
missing word is forgivable by a 'so close' yellow error, allowing the missing
word to be slot in."

**Shape:** on submit, before anything is graded, if the tray is exactly the
target minus ONE word (all others present, in order) and the answer is ≥6
tiles, the step shows an amber "So close — one word is missing" and returns.
No `onComplete`, no `submitted`: the tray stays live, the CTA stays "Check",
and the answer is NOT revealed — the grace is a second look at your own tray,
not a hint. Spent once per step; a second omission grades red normally.

The 6-tile floor is the ruling worth keeping: on a four-tile answer the
missing word usually IS the lesson (a particle drill is exactly "which one,
and is it there"), so forgiving it would forgive the thing being tested.

`Feedback` grew a fourth tone (`soClose`) — amber like `flagged`, but over an
unfinished attempt rather than a win, so it takes the warning triangle instead
of the success check. Icon plus text, never colour alone.

Tests: `BuildSentenceSoClose.test.tsx` (8) — the detector's unit cases
including duplicated words, the banner, the repair-and-pass path, grace
exhaustion, the short-answer refusal, and a transposition NOT triggering it.

### 4a. A latent trap found writing the test — no shipped impact

Without a `targetSentence`, `BuildSentenceStepView` seeds the leniency
expansion from `correctOrder.join(" ")` — TILE spacing, not bunsetsu spacing.
`scrambleVariants` then treats a bare `が` as its own movable chunk and emits
「が こども すき だ から えんぴつ を」 as an ACCEPTED answer: particle before
its noun, ungrammatical, graded correct.

Checked before reporting it as a bug: **all 2,489 shipped word-granularity
build steps carry a `targetSentence`**, so the fallback never runs in
production. Worth a guard if that ever stops being true.

## 5. Grammar rule cards are a wall of prose — COURSE-WIDE · m31 FIXED

**Seen:** `ja-m31-neo-2` step 0. Spencer: "still long as hell."

**Measured** (375×667, stage `scrollHeight`): **1541px of scroll on a 455px
stage** — 3.4 screens. **1124px of that (73%) was the rule prose alone**,
rendered as 12 bullets, five of which carried no Japanese at all:

> 3. Look hard at what changed and what did not.
> 5. The verb still comes last.
> 8. Lesson eleven is about exactly that disappearance.
> 10. They are ONE EVENT DESCRIBED FROM OPPOSITE ENDS.
> 12. Everything else in this module is a consequence of that.

**Cause: unbounded drift.** Nothing caps rule length — `lesson-authoring-guide.md`
§162 specifies examples, antiPattern and cultureNote but says nothing about the
`rule` string. Across all 231 authored cards it has grown monotonically:

| | m6 | m12 | m17 | m22 | m27 | m31 |
|---|---|---|---|---|---|---|
| mean chars | 169 | 262 | 604 | 811 | 1002 | **1214** |
| sentences/card | 2.1 | 3.3 | 4.9 | 7.2 | 8.4 | **9.2** |
| % of sentences containing any Japanese | 96% | 93% | 73% | 77% | 83% | **59%** |
| forward-references to other lessons | 0 | 0 | 2 | 4 | 8 | **19** |

That last row is the real finding. It is not only that the cards got longer —
the **ratio inverted**. An m6 card was almost entirely worked example; an m31
card is 41% English commentary about the course, and each module carries ~19
sentences that are pure forward-reference ("lesson eleven is about…"). Those
teach nothing about the point on screen.

**Fix (m31 only):** all 9 rule cards rewritten. Every rule-bearing claim kept,
every connective sentence and forward-reference cut. Mean **1214 → 758 chars
(−38%)**. On the card Spencer flagged:

| | before | after |
|---|---|---|
| stage scroll @375×667 | 1541px | **931px** (−40%) |
| rule prose | 1124px / 12 bullets | **514px / 3 bullets** |

**Not fixed — needs a ruling.** (a) A course-wide sweep of the other 222 cards;
m17–m30 all sit in the same band. (b) A machine cap so it cannot drift again —
the repo enforces everything else this way, but the number is a curriculum call
and I have not picked one unilaterally.

**Separate observation, same step.** Lessons render `variant="compact"`
(`StepRenderer.tsx:195`, Workshop A 2026-07-12), which shows the title, the
full rule, and **the first example only** — the other 4 authored examples and
the `antiPattern` tile never render in a lesson. So the card is prose-heavy by
construction: the Japanese is dropped and the English is not. Trading prose for
one or two more example tiles would move the ratio back towards m6's without
adding height. That reverts a documented decision, so it is Spencer's call.

## 6. 医者 (and 208 other words) can never show kanji — COURSE-WIDE · OPEN

**Seen:** `ja-m31-neo-2` listening step — 「いしゃが **母**に くすりを くれる」.
Spencer: "dont we teach isha? or is that supposed to be non kanji". Not
intentional: 母 unlocks at m8 and renders, いしゃ sits beside it in kana.

**Cause:** the atom already carries the spelling — `courseAtoms.ts:616`,
`{ id: "isha", kana: "いしゃ", kanji: "医者", … fromModule: "m20" }`. The blocker
is the catalog. `N5_KANJI` holds **147 glyphs and stops introducing at module
27**; 医 and 者 are in neither. `applyKanjiSurfaces` can only substitute glyphs
the catalog knows, so the word is frozen in kana permanently.

**Scope:** of the 386 atoms carrying a kanji spelling, **208 (54%) are blocked
by ≥1 missing glyph** — 215 distinct glyphs. **165 of those 208 are blocked by
exactly one missing glyph**, so a small catalog addition unblocks most of it.
m28–m31 introduce **zero** new glyphs, so the entire N4 tier reads at the m27
kanji level. Worst offenders by atoms blocked: 曜(7) 御(4) 飯(4) 風(3) 晩(3).

The mechanism to fix it already exists and needs no new code: `KanjiEntry.tier`
(`n5Kanji.ts:19`) — `"exposure"` marks a non-N5 glyph the course uses constantly
(明日, 家, 友達, 時計 are already in on that basis). 医者 is exactly that case.
The work is authoring catalog rows with module assignments, not engineering.

Related to **2a** (花): same symptom, different cause — 花 IS in the catalog and
is blocked by the homograph gate instead. Both belong in the same audit item.

## 8. Local draft harness was emitting unusable output — FIXED

Spencer asked for the local model to be used or at least exercised. Running
`scripts/draft/generate.mjs m31` surfaced three defects in the harness itself,
all of which made its output unusable for this course rather than merely bland:

1. **Every draft came out in ます-form.** `frames.mjs` defined `buildPlain` for
   all three verbs and `toBeat` never called it — dead code since the harness
   was written. 25 of the 26 IR modules declare `register: plain`, and for m31
   specifically `m31-neo.test.ts:602` makes polite forms a hard failure, so
   100% of output was unusable and nothing said so.
2. **Past-tense glosses on non-past sentences** (inv 17 / GATE 8) — 8 of 23 in
   one run. `en` is the one field the frame does not build, so the frame could
   not see it. Fixed in the prompt (the model now writes them correctly) with a
   `check()` backstop rather than filtering alone.
3. **もらう glossed from the giver's side** — "my friend gave me a photograph"
   on a もらう sentence, which is くれる's gloss and erases the one thing もらう
   teaches.
4. **Every drafted くれる sentence contained わたしに** — grammatical, and the
   exact shape L10 spends a lesson teaching learners *not* to write. The frame
   now drops the receiver and switches は→が when the receiver is わたし.

Verdict unchanged from the 2026-08-14 measurement and worth restating: the
harness drafts *candidates*. Reading this run's output, the mechanically-clean
sentences still included あめ (the kana homograph) and a family giving sake to a
teacher. **A gate's pass rate is not a quality measure.**
