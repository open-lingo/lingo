### b. Create an Auth0 **Native** application — NOT needed yet

**The app runs with auth bypassed** (`VITE_NATIVE_AUTH_BYPASS=true` in `.env.native`), so
you can get it on your phone and check layout today without anyone touching Auth0. A
bypassed build paints a permanent red **NO AUTH** badge bottom-left so it can't be confused

Do this section when you want real accounts on the phone:

⚠️ **Do not add the callback URLs to the existing SPA application.** That one serves
app.openlingoapp.com; editing it is editing production auth config to ship a test build.
A second Auth0 app costs nothing and keeps the blast radius at zero.

Auth0 Dashboard → Applications → **Create Application** → type **Native**. Then:

- **Allowed Callback URLs** and **Allowed Logout URLs** — both get exactly:
  ```
  com.openlingo.app://dev-txjdn01ew3dmaecy.us.auth0.com/capacitor/com.openlingo.app/callback
  ```
  Auth0 checks those two lists separately; a missing logout entry fails with a full-screen
  Auth0 error page the app cannot catch.
- **Settings → Advanced → Grant Types** → tick **Refresh Token**. Without it the learner is
  logged out on every cold launch: WKWebView's ITP blocks the silent-auth iframe Auth0
  would otherwise re-hydrate a session from, which is why the native build uses refresh
  tokens in localStorage instead.
- Copy the **Client ID** into `.env.native` as `VITE_AUTH0_CLIENT_ID`.

`.env.native` already exists locally with everything else filled in (API base pointed at the
prod Lambda). It is gitignored.

### e. Getting it onto the phone — the four gotchas

All four of these cost real time on 2026-08-07. None of them announce themselves.

**1. Xcode won't list the device → Developer Mode is off.** Not a cable problem. Diagnose it
without guessing:

```bash
xcrun devicectl list devices          # look for "connected (no DDI)"
```

`(no DDI)` means the Developer Disk Image can't mount, which is what Developer Mode gates.
A charge-only cable shows *nothing at all* here, so if the device is listed the cable is
fine. For the definitive read, `--json-output` a file and check
`deviceProperties.developerModeStatus`; the human-readable table doesn't print it.

Fix on the phone: **Settings → Privacy & Security → Developer Mode** → on → reboot. That
menu item only exists after the phone has been plugged into a Mac running Xcode.

**2. The build hangs for ten minutes at `CodeSign` → a keychain dialog is waiting.** It is
often *behind* the Xcode window, and `xcodebuild` gives no hint. Detect it:

```bash
pgrep -fl SecurityAgent    # if this is running, a modal is on screen
```

Click **Always Allow**, not *Allow* — the build signs four separate things (Cordova.framework,
Capacitor.framework, App.debug.dylib, App.app) and *Allow* re-prompts for each.

**3. First launch is refused even though install succeeded.** Expected:

> Unable to launch com.openlingo.app because it has an invalid code signature, inadequate
> entitlements or its profile has not been explicitly trusted by the user.

Trust it: **Settings → General → VPN & Device Management → Apple Development: <your
Apple ID> → Trust.** That entry only appears once an app signed by the cert is installed.

**4. Trust appears to do nothing → reboot the phone.** "Verify App" is a *network* call to
Apple; it fails silently with no spinner and no error when it can't get through (VPN, DNS
filtering, captive portal, Low Data Mode). It also caches: on 2026-08-07 trust was granted
but SpringBoard kept refusing until a restart, because the trust state is read at launch.
**If trust looks granted and launch still fails, restart the phone before debugging anything
else.**

### f. Install from the CLI instead of pressing ▶

## 3. Two app-specific bugs found and fixed while wiring this

Neither is boilerplate; both would have shipped a broken app.

**a. The first screen of a cold install was a dead end.** Every anonymous visitor renders
`MarketingRedirect` (it backs both `RootRoute` and `RequireAuth`), which calls
`window.location.replace()` to a *different origin*. In a Capacitor app that does not
navigate the webview — iOS hands the URL to Safari and leaves the app sitting on the
loading text with no route and no way back. That is the state a brand-new install boots
into, before anyone has ever logged in. Native now routes to the in-app `/login` instead.

**b. The speaking step would have hard-crashed the app.** `getUserMedia` with no
`NSMicrophoneUsageDescription` in `Info.plist` is a **termination**, not a denied
permission — it cannot be caught in JS. Added, along with
`NSSpeechRecognitionUsageDescription` for the `webkitSpeechRecognition` path.

Also added by hand (⚠️ `cap sync` does not do this): `CFBundleURLTypes` registering
`com.openlingo.app://`. Without it Auth0's redirect goes nowhere, the login sheet succeeds,
and the app stays anonymous with no error anywhere.

**Runtime checks.** `vite preview` over the web `dist/`, Playwright watching every request:

- Three public routes at 390×844: **the Capacitor chunk is fetched 0 times**, pages render,
  0 CSP violations. `/login` logs one 403 — Auth0 rejecting `localhost:4173` as an
  unregistered origin. The **pre-change baseline build produces the identical 403**, so it is
  environmental, not a regression.
- Manifest is served as `application/manifest+json` (not the SPA fallback), parses, and

native branches are **not** dead-code-eliminated from the web bundle — they ship and never
execute. That is the 1,232 bytes. The trade is deliberate: a native build that forgets the
env flag fails loudly instead of silently shipping auth that can never redirect back.

## 5. Known gaps — read before assuming it works on device

**1. Audio — was silent on hardware. Root cause found and fixed 2026-08-07: the wrong host.**

Not CORS, not `CapacitorHttp`, not the base64 bridge. `.env.native` set

```
VITE_ASSET_BASE_URL=https://openlingoapp.com     # the MARKETING apex
```

and the clips live on `app.openlingoapp.com`. Measured:

```
https://app.openlingoapp.com/tts/v1/ja/000566f1e2d51fac.mp3 -> 200  audio/mpeg  10,656 B
https://openlingoapp.com/tts/v1/ja/000566f1e2d51fac.mp3     -> 200  text/html   29,353 B
```

The apex does **not** 404 an unknown path — it returns the marketing site's SPA shell at
HTTP **200**. So the fetch succeeded, `decodeAudioData` rejected 29 KB of HTML, `loadBuffer`
caught that and `console.warn`ed, and lessons played through in silence with nothing on
screen to suggest a misconfiguration. Every layer behaved exactly as written.

What made it survive review: the value is identical to `VITE_MARKETING_ORIGIN` three lines
above it in the same file, where it is correct. Two different hosts, one string.

Fixed in `.env.native`, `.env.native.example` (now `https://app.openlingoapp.com`) and
`.env.example` (now empty — web resolves same-origin and `deploy.yml` passes no asset base,
so this variable has never applied to a web build). `fetchBinaryNative` now rejects a
`text/html` body outright and names the likely env cause, so a recurrence says so instead of
going quiet; `nativeHttp.test.ts` covers that plus a template ratchet asserting neither env
file ever points the asset base at the apex again.

⚠️ The general lesson, worth more than the fix: **on this CDN a 200 is not evidence of an
asset.** Any "did the file load" check against the apex must assert the content type.

**1b. The rest of the audio path — the part that was right all along.**
The web app resolves TTS clips **same-origin** (`assetUrl` returns a relative path);
CloudFront fronts both the app and `/tts/*`. In a Capacitor app the bundle is served from
`capacitor://localhost`, so `/tts/v1/ja/…mp3` resolves *into the app bundle*, where no mp3s
exist. Silence.

An absolute `VITE_ASSET_BASE_URL` is only half the fix: playback is `fetch` +
`decodeAudioData`, which **is** CORS-enforced, and the bucket sends no
`Access-Control-Allow-Origin`. It would fail *halfway* — `<audio>`-element paths keep
working while every Web Audio clip dies — the hardest version to notice.

The other half is `shared/platform/nativeHttp.ts`: on native that one fetch goes through
`CapacitorHttp`, i.e. the native URLSession, so no origin is attached and no CORS preflight
happens. **This avoids needing a CloudFront policy change from Trevor at all.**

This half was never the problem — but it is still required, and it is why no CloudFront
policy change from Trevor is needed. Keep both.

**2. Offline is a prerequisite, not a nice-to-have.** App Store Guideline 4.2 (Minimum
Functionality) rejects thin web wrappers. Submission needs the service worker + per-module
audio packs from the scoping doc, not just this shell.

**3. Store submission fires the trademark tripwire** — OPEN LINGO, Class 9, $350, before
any submission. Deliberately deferred (`docs/ECONOMICS.md`).

**4. Theme flash.** The launch background is the light preset (`#f5f0e6`). A learner on the
dark preset gets a cream flash on every cold launch; fixing it properly means persisting
the theme natively.

**5. Not yet verified on hardware.** Nothing below has been executed on a device: the auth
round-trip, the deep link, mic permission, layout under the notch. The build itself is
verified only as far as the platform component allows (§2a).
