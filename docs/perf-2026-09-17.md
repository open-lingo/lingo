**Finding.** 72.3% of the IPA's compressed weight (21.18 MB of 29.27 MB) is
the Kuromoji dictionary + ONNX runtime WASM — both lazily `import()`-loaded
(`src/features/languages/ja/readingAnnotation/kuroshiro.ts`,
`src/shared/speech/whisper-worker.ts`) and used only for: (a) converting a
kanji-bearing ASR transcript back to kana for scoring on JA speaking steps,
and (b) the opt-in Whisper fallback engine (`?speech-engine=whisper`, gated
behind `speech/featureFlag.ts`; native on-device recognition is the default —
see `[[native-speech-recognition]]`). Neither is on the learner's cold-open
critical path — but both ship in **every** install regardless of whether the
user ever triggers them.

### What App Thinning would and would not remove

App Store "app thinning" (slicing) operates on exactly three things: (1)
asset-catalog (`.xcassets`/`Assets.car`) variants per device idiom/scale/
memory class, (2) architecture slices (irrelevant — this is already
single-arch `arm64` for App Store distribution, no armv7/bitcode), (3)
On-Demand Resources explicitly tagged as such in Xcode. **This IPA's
`Assets.car` is 79,071 bytes compressed (0.3% of the total) and there are no
ODR tags** (checked: no `NSBundleResourceRequest`/ODR tag usage in the
`ios/` project). Everything else — `public/dict/`, the ONNX wasm, every JS
chunk, every content JSON file, every image under `public/img|noto-emoji|
region-flags|lingo-art` — is a plain file inside Capacitor's `webDir`, not an
asset-catalog member, so thinning's slicing engine treats it as opaque and
ships it whole to **every** device/OS combination. **App Thinning removes at
most ~0.3% of this IPA (icon variants); it does not touch the 72.3% dict+wasm
block, or any other `public/` asset.**

**Verdict: SKIP (no A4 action).** Shrinking the dict/WASM block is a real
lever (72.3% of download, 21.18 MB) but requires either (a) converting the
kanji-ASR-fallback path to fetch the dictionary on first use from a CDN
instead of bundling it, or (b) dropping Whisper's bundled ONNX runtime in
favor of loading it from a CDN when the feature flag is actually turned on —
both are content-delivery/feature-flag architecture calls outside this lane's
owned files (`src/features/languages/ja/readingAnnotation/`,
`src/shared/speech/`) and outside a ≤1 h budget. Flagged for the lead with
the number: **21.18 MB / 72.3% of the IPA, zero cold-open cost today**.

### 1a (continued) — Lane A4c (2026-09-17): the A4b landmine, and the dict
prune is **SKIP** for now

A4b's "code landed, prune is safe-by-default" claim had a real bug: it
gated the CDN path on `VITE_ASSET_BASE_URL` alone. The shipped build-25
`.env.native` sets `VITE_ASSET_BASE_URL` to
`https://app.openlingoapp.com` (it's the TTS asset base, not a dict-CDN
signal), and `vite build --mode native` loads that file — so
`import.meta.env.VITE_ASSET_BASE_URL` is set on every native build today,
while the shell `process.env.VITE_ASSET_BASE_URL` that
`prune-native-assets.mjs` reads is not. If shipped as-is: `kuroshiro.ts`
would have started fetching the 15 MB dict over the network on the native
app's first JA speaking step (no CDN copy is even published yet, and no
persistent on-device cache exists — every cold `getInstance()` re-fetches),
while the bundled copy would still ship in the IPA at the same time
(`prune-native-assets.mjs`'s check never actually tripped because it reads
a different env source) — worst of both: no size win, plus a new
network-dependency + offline-breakage risk on a step every JA learner
hits.

**Lead decision: the dict stays BUNDLED. Fixed by requiring TWO env vars,
both explicit opt-in, in both `kuroshiro.ts` and `prune-native-assets.mjs`:
`VITE_DICT_FROM_CDN === "1"` AND `VITE_ASSET_BASE_URL` set.** Neither is
set anywhere in this repo today (checked: not in `.env.native`, not in CI),
so this is a no-op — verified live, not assumed: a plain
`npm run build:native` compiles `DICT_PATH` to the literal `"/dict/"`
(`dist/assets/kuroshiro-*.js`) and ships `dist/dict` at 19,880 KB
uncompressed (`du -sk`); `npm run build` (web) is byte-identical in that
respect (`"/dict/"`, `dist/dict` at 19,880 KB). The Whisper/ONNX exclusion
(A4b's job 1, this lane's task-4 verification) is confirmed **DO**,
unaffected by any of this: `ort-wasm-simd-threaded*.wasm` /
`onnxruntime-web*` / `whisper-worker*` / `transformers.web*` are absent
from the native `dist/assets` and present on the web build's `dist/assets`
— the `--mode native` alias in `vite.config.ts` is doing exactly what it
should.

**Verdict: SKIP (dict prune), same as A4's original top-line finding —
now with the numbers that decide it.** Per JA install: **15 MB shipped
once in the IPA vs. 15 MB fetched over the network with no persistent
cache on every cold dict init** (today's patch has no cache layer — see
`kuroshiro.ts`'s file header) — a wash on total bytes moved, and strictly
worse for the learner: a slow/failed fetch degrades a first-speaking-step
experience that works offline today into one that doesn't. **Precondition
to revisit:** (1) a persistent on-device cache in `kuroshiro.ts` (Cache
API or similar) so the 15 MB is paid once per device, not once per cold
init, and (2) a **versioned** `/dict/v1/` CDN prefix, not a bare `/dict/`
— `deploy.yml`'s root sync (`aws s3 sync dist/ s3://… --delete`, no `dict/`
exclude, confirmed by grep) would delete an unversioned CDN copy out from
under every installed native app the next time a **web** build ships
without `dist/dict` present (web never populates `dist/dict` under a CDN
build the same way native would — same two-gate check, opposite platform).
Neither precondition is this lane's to build; flagged for Spencer/Trevor
alongside the still-unpublished CDN copy A4b already flagged.

## 5. `DecompressionStream` + gzip-at-rest for content JSON

### Availability — live, in Mobile Safari on the actual simulator device

`src/shared/dev/simProbe.ts` is **dirty** in `git status` (another lane's
in-flight change), so per the task's own fallback rule I did not touch it.
Instead: `safaridriver -p 4444` (already installed, Safari 26.6.2) can drive
a real WebDriver session against **Mobile Safari inside the booted
simulator** — not literally the Capacitor WKWebView shell (no scriptable
eval channel into a 3rd-party app's WKWebView exists anywhere in this repo
or via `safaridriver`, which only automates Safari/STP browser sessions —
confirmed live: `safari:useSimulator` alone was rejected with "platform
incompatible", it needed an explicit `platformName: "iOS"` capability too),
but the **same WebKit build** as the app (both are iOS 26.5's system
WebKit), so the feature-support answer is identical.

```
POST /session {browserName: safari, platformName: iOS, safari:useSimulator: true,
               safari:deviceUDID: <iPad Air 11" (M4) UDID>}
→ session capabilities: safari:platformVersion=26.5, safari:platformBuildVersion=23F77,
  safari:deviceType=iPad
POST /session/<id>/url → http://localhost:5399/ja/learn
POST /session/<id>/execute/sync → { typeof DecompressionStream !== "undefined",
                                     typeof CompressionStream !== "undefined" }
→ { decompressionStream: true, compressionStream: true }
```

**`DecompressionStream: true`, `CompressionStream: true` — confirmed live on
iOS/Safari 26.5 (build 23F77), iPad Air 11" (M4) simulator.** (`DecompressionStream`
shipped in WebKit well before this OS version; this review confirms presence
directly rather than citing that history.)

### JSON.parse vs gunzip+parse timing — **measured in Node** (proxy; not the
simulator — chosen for speed/reliability within the time budget; V8, not
JavaScriptCore, so treat as directional, not exact)

Largest ja content module: `src/pub/content/v1/ja/m26.4b8ead4729.json`,
248,857 bytes raw. Gzipped at level 9 for the comparison: 31,872 bytes
(87.2% smaller). `node scratchpad/review/gzip-bench.mjs`, n=200 iterations
each, warmed up first:

| operation | ms/iter |
|---|---:|
| `JSON.parse` only (string already resident) | 0.396 |
| `zlib.gunzipSync` only | 0.425 |
| `gunzip` + `JSON.parse` (as if just fetched compressed) | 0.855 |

**Cross-check against Task 1's IPA data:** the IPA's own zip DEFLATE
compression on this exact file already achieves 32,317 bytes (see Task 1's
top-15 table context — `m26...json` compressed entry) — within 1.4% of the
standalone `gzip -9` result (31,872 bytes). **The App Store download is
already near-optimally compressed by the IPA container itself; gzip-at-rest
would not shrink the download.**

**Where gzip-at-rest WOULD help: on-device storage after install.** iOS
extracts the IPA's zip contents to plain files on the device's filesystem at
install time — the ~13.3 MB of `src/pub` content JSON sits on-disk at its
raw, uncompressed size once installed, not at the zip-compressed size. At
the measured 87.2% compression ratio, pre-gzipping all content JSON and
decompressing via `DecompressionStream` on load would save roughly
**13.3 MB × 0.872 ≈ 11.6 MB of on-device storage**, for **+0.46 ms of CPU per
module load** (0.855 − 0.396 ms) — negligible against the 0.36 s cold-open
budget, and paid only once per module (loaded lazily, per the existing
per-language `content/v1/<lang>/mN.<hash>.json` scheme already documented in
`content-as-data-2026-09-13.md`).

**Verdict: DO (recommend), not landed by this lane.** Real, measured,
~11.6 MB on-device storage win with a negligible (<0.5 ms/module) CPU cost
and a confirmed-available decoding API (`DecompressionStream`, live-tested
above). Not landed here because it means changing how content JSON is
fetched/decoded (`src/shared/content`-adjacent loading code, plus a build
step to emit `.gz` copies) — outside this lane's owned files
(`src/features/learn/**`, `vite.config.ts` visualizer-only) and a
multi-file, >1 h change. Flagged for the content-delivery owner with the
exact numbers above.
