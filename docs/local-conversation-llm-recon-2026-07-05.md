# Local Conversation LLM — Feasibility Recon

**Date:** 2026-07-05
**Question:** Can a very small local LLM, mechanically gated by our own conjugation engine + per-learner knowledge state, act as a Japanese conversation partner that *literally cannot* produce language above the learner's level — with local TTS speaking the replies?
**Answer:** Yes, and the pieces are unusually well-aligned. This is buildable in a weekend at v0 quality.

---

## TL;DR

Serve a **JA-native ~1.2B model (LiquidAI LFM2.5-1.2B-JP)** on the beast via **llama.cpp `llama-server` (Vulkan backend)** — the RX 9070 does ~85–100 tok/s on 8–9B Q4, so a 1.2B reply of 30 tokens lands in well under half a second. Wrap it in a **post-hoc validate-and-repair loop**: morphological analysis (fugashi+UniDic or Vibrato) lemmatizes every token and checks it against `getUnlockedAtomIds()`; conjugated forms are checked against a precomputed surface-form set generated by our own `conjugateVerb`/`conjugateIAdj`; unknown kanji are deterministically downgraded to kana using the analyzer's readings. Failures regenerate with the offending word named in the prompt (max 2 retries, then a canned template reply). This exact shape — soft steering + mechanical post-hoc gate, not hard token masking — is what the one directly-comparable published system did ([arXiv 2506.04072](https://arxiv.org/html/2506.04072v2)), and our known-pool sizes (≈126 words at module 5, ≈343 at module 15) are small enough to enumerate *in the system prompt itself*. TTS is **VOICEVOX ENGINE (Nemo voices), CPU-only Docker container** — commercial use OK with a credit line, explicit `speedScale` for slow/clear learner speech, no GPU contention with the LLM. Hard constrained decoding (llguidance) is viable for Japanese — byte-level engines genuinely solve the BPE-split problem — and stays in our pocket for a v2 "constrained slots" mode. Fine-tuning is **not needed for v0**; if prompting can't hold the register, LoRA on **Sarashina2.2-3B (MIT)** via mlx-lm on an M5 Max is an hours-scale job.

## 0. What we already have (codebase grounding)

The three claimed assets are real, and one is even better-shaped than expected:

**Conjugation engine** — `/home/beast/projects/lingle/lingo/src/features/languages/ja/conjugationEngine.ts`:
- `conjugateVerb(dictionary, group, form)` — 12 `ChainForm` verb forms (masu/masu-neg/masu-past/masu-past-neg/te/ta/nai/tai + 4 chained tai/nai stacks); `conjugateIAdj(dictionary, form)` — 3 forms.
- Ground truth: `conjugationTables.ts` — **45 verbs + 41 adjectives = 86 entries** (the "88" in the test title is slightly stale), each with `introducedAtModule`, plus `getVerbsUpToModule()` / `getAdjsUpToModule()` module-scoping helpers already built.
- **Direction: generate-only.** There is no parse/validate function — but that's fine: for validation we *precompute all legal surface forms* of the learner's unlocked verbs/adjectives (45 × ~13 + adjective forms ≈ a few hundred strings) into a set, and validation becomes an O(1) lookup. The generator is exactly the tool needed to build the gate.

**Per-learner knowledge state** — three queryable sets, all already implemented:
- Vocab whitelist: `getUnlockedAtomIds(): Set<string>` (`src/features/lesson/data/unlockLessonAtoms.ts`), server-mirrored at `GET /progress/me/unlocks` (lingo-core `app/progress/router.py`). Lemma = `CourseAtom.kana`, written form = `kanji?`, from `JA_COURSE_ATOMS` (749 atoms total; ~531 authored, 218 marked `"future"`).
- Grammar whitelist: `getActiveGrammarPoints()` (`src/features/flashcards/engine/grammarSrs.ts`) over the 93-point registry `n5-grammar-points.json` (m3–m29).
- Kanji whitelist: `getKanjiUpToModule(currentModule)` over `N5_KANJI` (99 kanji, introduced from m8; drill-side exposure gate `KANJI_EXPOSURE_MODULE = 10` in `DrillQuestionCard.tsx`).

**Pool sizes make this *easier* than the generic problem:**

| Learner at… | Known vocab (cumulative) | Known grammar points | Known kanji |
|---|---|---|---|
| Module 5 | ≈126 atoms | ≈11 | 0 |
| Module 10 | ≈245 atoms | ≈33 | ~small set |
| Module 15 | ≈343 atoms | ≈58 | growing |
| Full N5 (m27) | ≈531 atoms | 93 | 99 |

A 126–343-word whitelist fits **inside the system prompt** (a few hundred tokens) *and* compiles into a trivially small constraint grammar. Most published "vocabulary-constrained generation" work fights whitelists of thousands of words; ours is two orders of magnitude smaller at the beginner levels where the feature matters most.

**Existing precedent for local models:** the current TTS pipeline (`lingo-core/scripts/tts/generate.py`) already runs **Kokoro (82M, CPU) locally in a dedicated venv** with a `TtsProvider` abstraction — the local-model operational pattern exists in this repo. Note the divergence: `docs/TTS_PLANNING.md` (ElevenLabs live-API design) was never built; reality is the precomputed static-manifest pipeline in `src/shared/tts/index.ts`.

**Gaps (both fine for v0):** zero existing LLM integration, zero websocket/SSE infrastructure — v0 is plain request/response REST, consistent with everything else in the app.

### Will a 1–2B model hold "simple Japanese only" via prompting?

Partially — and measurably better on JA-native, instruction-tuned models than generic multilingual ones (the M-IFEval-ja spread above is large). Evidence that prompting alone is *not* fully sufficient at easy levels: "Right at My Level" finds prompt-only lexical simplification performs poorly at beginner levels and for non-English including JLPT ([arXiv 2604.05302](https://arxiv.org/abs/2604.05302)). **This is fine for us** — we never rely on the prompt for the guarantee. The prompt's job is only to make the *first-pass gate rate* high; the mechanical gate provides the guarantee (§3). Design consequence: pick the model that maximizes first-pass compliance per parameter → LFM2.5-1.2B-JP.

## 2. Fine-tune or not?

**v0: don't.** Evaluate the ceiling of {JA-native small model + whitelist-in-prompt + few-shot exemplars of the target register + low temperature + `logit_bias` nudges + mechanical gate} first. The gate makes prompt failures cheap (a retry), not fatal. Measure first-pass gate rate before spending any training effort.

**If first-pass rate is too low (say <50% even after prompt iteration):** LoRA on synthetic dialogues is the self-cleaning play —
1. Generate 10–50k short scenario dialogues with a frontier model, *each constrained to a module-N vocab list*.
2. **Filter every line through our own validator** (the same gate from §3) — training data that provably respects the constraint. Garbage never enters.
3. LoRA/QLoRA the base model on the filtered set; optionally DPO with gate-passing vs gate-failing pairs.

**Hardware reality for training:**
- **M5 Max + mlx-lm: the clean path.** M5 Pro/Max MacBook Pros shipped March 11, 2026 ([Apple Newsroom](https://www.apple.com/newsroom/2026/03/apple-introduces-macbook-pro-with-all-new-m5-pro-and-m5-max/)) — M5 Max: 128GB unified, ~600–614 GB/s, Neural Accelerators in every GPU core. `mlx-lm` + `mlx-lm-lora` cover SFT/LoRA/QLoRA/DPO (plus ORPO/GRPO), Qwen3 and Gemma 3 supported, 4-bit training supported ([mlx-lm-lora](https://pypi.org/project/mlx-lm-lora/)). Proxy throughput: ~285–296 tok/s LoRA training on an 8B on M4-Max-class ([TDS writeup](https://towardsdatascience.com/lora-fine-tuning-on-your-apple-silicon-macbook-432c7dab614a/)); our dataset (10–50k × ~200 tok ≈ 2–10M tokens) ⇒ **~2h/epoch on an 8B at 10k examples, under an hour per epoch for a 1–3B; 50k examples on a 1–3B ≈ a few hours/epoch** — an overnight job at worst `[extrapolated from M4-class proxies — pilot: time 100 iters, multiply]`.
- **RX 9070 (ROCm): possible, still the rough road.** gfx1201 is now in PyTorch ROCm wheels (2.9.x), bitsandbytes lists gfx1201 (AMD backend still "preview"), and Unsloth has official AMD support ([docs](https://unsloth.ai/docs/get-started/install/amd)) — but AMD's QLoRA validation was on MI300X, and there are no clean "worked on a 9070" reports yet `[training-knowledge — verify by trying; no RDNA4-specific axolotl/LLaMA-Factory success report found]`. Don't make the 9070 the training dependency; it's the inference box.
- Sarashina2.2-3B (MIT) is the ideal fine-tune base license-wise; LFM1.0 also permits derivatives.

## 3. The mechanical-grammar-check architecture (the heart)

### Recommended: post-hoc validate-and-repair, with soft steering to cut retries

There is near-exact prior art: **"Toward Beginner-Friendly LLMs for Language Learning"** ([arXiv 2506.04072](https://arxiv.org/html/2506.04072v2)) — Japanese conversation, JLPT-level vocabulary control, validation via **Sudachi lemmatization → exact match against JLPT vocab lists** (functionally our validator). They deliberately did *not* hard-mask to the whitelist; soft logit steering (FUDGE) lifted comprehensibility 39.4%→83.3% but still left ~8–12% token-miss-rate — i.e., **soft methods alone never guarantee; a mechanical gate is required regardless**. Our loop:

```
learner state ──► whitelist bundle (vocab lemmas + grammar points + kanji set
                  + precomputed conjugation surface forms)
       │
       ▼
1. GENERATE   llama-server: system prompt = scenario template + full whitelist
              + few-shot register exemplars; temp low; optional logit_bias
2. VALIDATE   (all sub-ms:)
              a. morphological analysis (fugashi+UniDic / Vibrato)
                 → every content-token lemma ∈ vocab whitelist?
              b. conjugated surfaces ∈ precomputed conjugation-form set?
                 (generated by conjugateVerb/conjugateIAdj over unlocked entries)
              c. grammar-pattern check vs getActiveGrammarPoints()
              d. kanji codepoints ∈ known-kanji set? (violations are REPAIRED, not rejected)
3a. PASS      → kanji-downgrade pass (unknown kanji → analyzer reading kana) → show + TTS
3b. FAIL      → REGENERATE with offending words named in the prompt
              ("使わないで: 冷蔵庫。使ってもいい: たべもの、みず…") — max 2 retries
3c. EXHAUSTED → canned scenario-appropriate template reply (always safe, always available)
```

**Key design trick — generate in kanji, display in kana.** Beginner text is mostly kana, and kana-only morphological analysis is the known weak spot (~79.7% macro accuracy on hiragana-only input vs high-90s mixed — [hiragana MA study](https://aircconline.com/csit/papers/vol11/csit112310.pdf)). So: let the model write natural kanji-mixed Japanese (which analyzers handle best), validate *that*, then deterministically downgrade unknown kanji to readings for display. The analyzer gets its disambiguation cues; the learner gets their level. Second mitigation: compile the whitelist into a **MeCab/Vibrato user dictionary** so known words segment deterministically; treat analyzer ambiguity as a validation failure → regenerate.

**Analyzer choice:** server-side **fugashi + UniDic** (MIT, explicit lemma + orthographic-variant layers — exactly what lemma-matching kana/kanji variants needs; [fugashi](https://github.com/polm/fugashi)) or **Vibrato** (Rust, ~2× MeCab, has [Python bindings](https://github.com/daac-tools/python-vibrato) and [WASM](https://jsr.io/@wangb/vibrato-wasm) for a future browser mode). Sudachi mode C is the academically-validated reference ([2506.04072](https://arxiv.org/html/2506.04072v2)) but slower. Browser-side later: kuromoji.js (`basic_form` lemma) or vibrato-wasm. A 20–40-char reply analyzes in **well under a millisecond** `[absolute chars/sec figure is training-knowledge — verify; the sub-ms-per-reply conclusion is robust]`.

### Hard constrained decoding: viable for Japanese — hold for v2

The BPE worry is real but **solved**: modern engines (llguidance, XGrammar) define constraints over **bytes** and compute token masks by walking a prefix-trie of the tokenizer's byte-level vocabulary — word↔token alignment never matters; multi-byte UTF-8 splits and boundary-spanning tokens are handled tokenizer-agnostically ([llguidance](https://github.com/guidance-ai/llguidance), [XGrammar-2](https://arxiv.org/pdf/2601.04426), [UTF-8 Plumbing](https://arxiv.org/abs/2511.05578)). Mask cost ≈ **50μs/token, p99 0.5ms** ([llama.cpp llguidance docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/llguidance.md)) — negligible. llama.cpp integrates llguidance behind `LLAMA_LLGUIDANCE=ON`; grammars are per-request.

Why it's not the v0 mechanism: (1) the whitelist is lemma-level but grammars constrain *surface strings* — you'd have to enumerate every allowed conjugation into the grammar, re-encoding the validator we already own (doable — our pool is small — but redundant); (2) hard-forcing degrades naturalness and can trap the model in valid-but-incoherent text ([AdapTrack](https://arxiv.org/pdf/2510.17376)); (3) the comparable published system avoided it for exactly this reason. **Where it shines later (v2): template skeletons with constrained slots** — grammar fixes the frame (particles/known patterns), whitelist-regex constrains only the content slots ([Prompt Sketching](https://arxiv.org/pdf/2311.04954)). If we ever go hard, use **llguidance, not native GBNF** — large word-alternation grammars are native GBNF's pathological slow case ([grammars README](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)).

### Latency math

- Generation: 30-token reply at ≥200 tok/s (1.2B Q4 on RX 9070 Vulkan) ≈ **0.15s**; TTFT tens of ms.
- Validation: **<1ms**. Conjugation set lookup: O(1).
- Expected retries: even at a pessimistic 50% first-pass rate, expected total ≈ 2 generations ≈ **0.3s**. Budget cap: 2 retries + canned fallback.
- VOICEVOX CPU synthesis of a short utterance: **sub-second** `[exact ms — verify on the beast]`.
- **End-to-end: comfortably inside "first token <1s, reply+TTS <3s"** — with enough headroom that a 3–4B model also fits if quality demands it.
- Consequence: post-hoc validation means no token-streaming to the user — irrelevant at these reply lengths, and VOICEVOX needs the full text anyway. Plain REST.

### Niche check

No existing project found that does LLM conversation with lemma-level whitelist enforcement for Japanese learners (closest: [sakubun](https://github.com/cubetastic33/sakubun) — kanji-set-filtered Tatoeba sentences; the 2506.04072 paper — soft steering only). **This is an open niche.**

## 4. Local Japanese TTS

## 5. Deployment shapes

### (a) Server-side on the beast — **the v0 shape**

- **llama.cpp Vulkan is the consensus-correct backend for RDNA4** — it currently *beats* ROCm/HIP and vLLM on this silicon: RX 9070 XT measured **62 tok/s on a 9B Q6** vs 48 for vLLM/ROCm ([benchmark](https://digtvbg.com/blog/llama-server-vulkan-rdna4-vllm-rocm-benchmark/)), **~80–103 tok/s on 8–9B Q4** ([scoreboard](https://knightli.com/en/2026/04/23/llama-cpp-gpu-benchmark-cuda-rocm-vulkan-scoreboard/), [techreviewer](https://www.techreviewer.com/tech-specs/amd-rx-9070-xt-gpu-for-llms/)). Extrapolated: **4B Q4 ≈ 130–180 tok/s, 1.2B ≫ 200 tok/s** `[no direct 1–4B RX 9070 bench found — verify on the box, it's a 10-minute test]`.
- ROCm status for the record: gfx1201 native Linux since ROCm 6.4.1; **ROCm 7.2 (Mar 2026) is the first with official RX 9070 WSL2 support** ([AMD WSL matrix](https://rocm.docs.amd.com/projects/radeon/en/latest/docs/compatibility/wsl/wsl_compatibility.html)) `[verify exact point release]`. **Not needed for inference — Vulkan sidesteps it entirely.** vLLM on consumer RDNA4: skip (no merged native gfx1201 quant kernels yet; [issue #28649](https://github.com/vllm-project/vllm/issues/28649)).
- **Per-request control:** `llama-server` exposes `grammar` (GBNF), `json_schema`, and `logit_bias` per request ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)) — exactly the knobs §3 wants. Ollama exposes only JSON-schema `format`, no raw GBNF/logit_bias ([docs](https://docs.ollama.com/capabilities/structured-outputs)) — fine for prototyping, wrong for production here.
- **Concurrency:** `--parallel N` continuous batching; a 4B Q4 leaves ~12GB for KV → **8–16 comfortable concurrent conversations, low-double-digits realistic** on one 9070 ([batching discussion](https://github.com/ggml-org/llama.cpp/discussions/4130)) `[load-test to confirm]`. A 1.2B model raises that ceiling substantially.

### (b) Fully in-browser — real, as a later privacy/offline mode

- WebGPU now ships in all four engines (Chrome/Edge, Safari 26, Firefox 141/145; Firefox Linux/Android still in progress) — ~85% global support ([web.dev](https://web.dev/blog/webgpu-supported-major-browsers), [caniuse](https://caniuse.com/webgpu)).
- **web-llm** carries Qwen3/Gemma-class small models; 0.5–3B Q4 at ~40–180 tok/s on good hardware, but **~8–12 tok/s for 3B on typical integrated-GPU laptops** ([web-llm](https://github.com/mlc-ai/web-llm)) `[perf figures blog-grade — verify]`. Download tax: ~0.6–1.8 GB one-time. LFM2.5-JP-in-browser would need an MLC compile `[unverified whether one exists]`.
- Validator runs in-browser too: kuromoji.js / vibrato-wasm + the conjugation engine is *already* TypeScript. TTS in-browser: Piper-WASM or `speechSynthesis`. **A fully-offline conversation partner is genuinely possible** — just not the v0.
- Honest ceiling: typical user laptop = 1–3B Q4, sluggish at the top of that; gaming PCs = 7–8B comfortably.

## 6. Concrete v0 recommendation

**Build (first weekend):**

*Day 1 — the loop, no UI:*
1. `llama-server` (Vulkan build) + LFM2.5-1.2B-JP Q4_K_M on the beast; confirm tok/s (expect >200).
2. Dump script: conjugation tables + course atoms + grammar points → a JSON "whitelist bundle" per module level (the TS data is the source of truth; a small `tsx` script exports it for Python).
3. Validator service in lingo-core: fugashi+UniDic (new venv, same pattern as `.venv-tts`) — lemma-check against bundle, surface-form set check, kanji pass. Unit-test it against hand-written pass/fail sentences *before* touching the LLM.
4. `POST /api/core/v1/converse`: scenario template + whitelist-in-prompt + few-shot → generate → validate → retry(≤2) → canned fallback. Log every attempt verdict.

*Day 2 — voice + eval:*
5. VOICEVOX ENGINE Docker (CPU) with a Nemo voice, `speedScale` ≈ 0.85–0.9; wire `converse` response → synthesis → audio back to client (reuse the Web Audio playback path in `src/shared/tts/index.ts`).
6. Three scenario templates (self-intro / ordering food / asking where something is — all coverable at module 5–7 vocab).
7. Scripted eval: 50 canned learner turns per scenario × 3 module levels → measure the metrics below. No UI needed yet; a dev page or curl is enough.

**Measure (go/no-go instrumentation):**
- **First-pass gate rate** (target: >70% with prompt iteration; <50% after tuning → trigger the fine-tune track).
- Retry distribution + canned-fallback rate (fallback >10% = model too weak or whitelist too tight).
- % tokens in-pool pre-gate (the soft-steering quality signal, à la Token-Miss-Rate in 2506.04072).
- Latency p50/p95: request→text, request→first audio (targets: <1s / <3s).
- Validator false-positive audit: manually review 100 *rejected* sentences — is the analyzer over-rejecting legitimate known-word usage (the kana-lemmatization risk)?
- Naturalness: Spencer reads 30 gate-passing replies cold; count "no human tutor would say this" instances.

**Explicitly deferred:** fine-tuning (until gate-rate data exists), llguidance slot-constraints (v2), in-browser mode, streaming, multi-turn memory beyond a short rolling window, any UI polish.
