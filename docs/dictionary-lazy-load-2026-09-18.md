# Japanese dictionary out of the install — phase 1 (2026-09-18)

Lane PACKS. Companion: `docs/project-review-2026-09-17-decisions-and-proposals.md` §2 item 2;
`docs/perf-2026-09-17.md` §1/§1a (lane A4b/A4c — landed the Whisper/ONNX exclusion, staged
but left the dict CDN path **SKIP** pending a persistent cache + versioned prefix). This
lane builds the missing precondition and wires it behind `dictionary.lazy`, default **OFF**.

## Correction to the brief's premise

The brief assumed the dictionary is "not needed before kanji recognition goes live at
module 8" (`KANJI_RECOGNITION_MODULE = 8`, `kanjiRollout.ts`). That constant gates when
KANJI SURFACES render in lesson content — it does not gate when the dictionary runs.
`SpeakingStepView.tsx` calls `warmKanjiReading()`/`convertToHiragana()` on **every** JA
speaking step unconditionally (`if (!isJa) return; warmKanjiReading();`), because Whisper
and even Safari's on-device recognizer return natural Japanese orthography (kanji)
regardless of what the curriculum is teaching in kana. Module 1 (`m1-ha.ts`, e.g.
`speaking("ja-ha3-speak-hito", "ひと", "person")`) already has speaking steps. **The
dictionary is a candidate to be needed starting at the learner's first JA speaking
step — inside module 1, not module 6 or 8.** `dictPrefetch.ts`'s `DICT_PREFETCH_MODULE`
is set to `1` accordingly (exported, trivially re-tunable). In practice this collapses to
"prefetch as soon as a JA learner opens the course" — there is very little lead time, which
is why the inline downloading state is the common case for a new install, not an edge case.

## Design

- **Storage**: the 12 `kuromoji` dict files (`src/pub/dict/*.dat.gz`, mirrored from
  `node_modules/kuromoji/dict` at build time) move to a versioned, immutable CDN prefix
  `/dict/v1/` on the same CloudFront distribution TTS already uses. Versioned so
  `deploy.yml`'s `aws s3 sync --delete` (no `dict/` exclude) can never delete an
  in-use object out from under an installed app; a future dict-format change ships as
  `/dict/v2/`, never overwriting `v1`. **Upload step for the lead (not done by this
  lane — AWS SSO is expired, per brief): `aws s3 cp src/pub/dict/
  s3://<site bucket>/dict/v1/ --recursive --cache-control
  "public,max-age=31536000,immutable"`.** Confirm the bucket name against
  `tts-publish/README.md`'s convention; no CloudFront invalidation needed for a new prefix.
- **Loader**: `dictLoader.ts` — cache-first, hash-verified (sha256 against the checked-in
  `src/shared/dict/manifest.json`, generated by `scripts/build/generate-dict-manifest.mjs`
  from the exact files `copyKuromojiDict` mirrors), gunzip on exit. Patches kuromoji's own
  swappable `BrowserDictionaryLoader.prototype.loadArrayBuffer` (`kuroshiro.ts`'s
  `patchDictLoaderOnce`) — native transports bytes via `fetchBinaryNative`/CapacitorHttp
  (the CDN sends no ACAO header; `capacitor://localhost` would be CORS-blocked otherwise),
  web via a plain same-origin `fetch`.
- **Persistent cache — one mechanism, both platforms, and why not the brief's split**:
  the brief suggested Capacitor `Filesystem` on native / Cache Storage on web. This lane
  uses **Cache Storage (`caches.open`/`.match`/`.put`) on both**, because
  `@capacitor/filesystem` is **not a current dependency**
  (`package.json` has `@capacitor-community/speech-recognition` +
  `@capacitor/{android,app,browser,core,ios}` — no `filesystem`), and the brief says not
  to add one without saying so. Cache Storage is a standard Web API already available
  inside Capacitor's WKWebView/Android WebView shell, so one code path serves both. Fails
  safe everywhere: no `caches` global, a `caches.open` throw, a full disk — every
  operation degrades to a silent no-op (`dictCache.ts`), never a crash, worst case = an
  uncached refetch next time. **Unverified**: this lane could not confirm Cache Storage
  persists reliably under the `capacitor://localhost` origin on a real device/simulator
  (no device run in this lane). If a device check shows it doesn't, `@capacitor/filesystem`
  (~1 day to add + wire) is the documented fallback.
- **Prefetch**: `dictPrefetch.ts`'s `triggerDictPrefetch(courseId, moduleIndex)`, called
  from `LessonStepEnvironment` (mounted by every lesson AND test-out route) on every
  step-type, not just speaking/typed — so it fires from the earliest lesson mount
  regardless of what step the learner opens first. No-ops instantly for non-JA courses,
  when the flag/CDN path isn't active, or once already started this session.
  **Not** Wi-Fi-gated: `@capacitor/network` is also not a current dependency, and the
  Network Information API (`navigator.connection`) that could substitute is WebKit/iOS-only
  absent — real, confirmed platform gap, not guessed — so it would only ever gate Android.
  Left ungated in phase 1 given the payload is one-time and ~17 MB; flagged for the lead.
- **Inline download state**: `useDictDownloadState.ts` (React hook on `kuroshiro.ts`'s
  exported `getDictLoadStatus`/`subscribeDictLoadStatus`, `useSyncExternalStore`). Wired
  into `SpeakingStepView.tsx`'s existing helper-text chain (lowest priority — never
  overrides an active listen/error/pass state): *"Downloading Japanese dictionary… kana
  answers still work."* Not yet wired into `TranslateStepView.tsx`'s typed-kanji-fallback
  path — flagged as a follow-up, not done by this lane.
- **Offline / CDN-unreachable fallback**: verified in code, not just asserted —
  `convertToHiragana`'s fast path (`if (!KANJI_RE.test(stripped)) return stripped;`) never
  touches the dictionary for pure-kana input, and a hash-mismatch or fetch failure throws
  into the SAME pre-existing graceful-degradation path (`kuroshiro.ts`, one `console.warn`,
  raw transcript used) — no new failure mode, only a new trigger for an old one.
- **Build step**: `dictionary.lazy` (`src/pub/feature-flags.json`) is read at build time —
  synchronously, via plain `fs`, not through the runtime-swappable `featureFlags.ts` path,
  because whether the dict is bundled is fixed the moment `vite build` runs and can't be
  changed by a post-deploy JSON edit like the rest of that file. `vite.config.ts` and
  `scripts/build/prune-native-assets.mjs` each read it independently
  (`scripts/build/readDictLazyFlag.mjs`) since `npm run build:native` runs them as two
  separate node processes. When on, `vite.config.ts`'s `copyKuromojiDict` plugin **deletes**
  `src/pub/dict` (not merely skips populating it — that directory is generated/gitignored
  and persists across builds on disk, and Vite always copies the entire `publicDir` into
  `dist` regardless of what any plugin did this run, so a stale copy from an earlier
  flag-OFF build would otherwise still ship). Verified live: flag OFF → `dist/` 75,980 KB,
  `dist/dict` present (12 files, unchanged from before this lane); flag ON (built locally,
  not committed) → `dist/` 56,112 KB, no `dist/dict` at all.

## Industry-standard note: CDN fetch-and-cache vs. ODR / Play Asset Delivery

Apple On-Demand Resources and Android Play Asset Delivery are both real, sanctioned
mechanisms — but both are single-platform, coupled to that store's packaging format
(Xcode `NSBundleResourceRequest` tags; Play's asset-pack app-bundle split), and neither
does anything for the web build. This is a Capacitor app shipping the same JS across iOS,
Android, and web from one codebase; a CDN fetch-and-cache is the one mechanism that works
identically on all three, needs no store-specific packaging, and lets the lead update or
roll back the dictionary object without an app-store resubmission. It also matches the
pattern already proven in this repo for TTS (`/tts/v1/*`, runtime-cached by the SW) and the
proposed per-course content packs (`/content/v2/*`) — one delivery mechanism, not three.

**Net effect on total bytes moved for a JA learner**: unchanged — they still fetch ~17 MB
either way (in the IPA, or over the network at module 1). The size win is for **non-JA
learners**, whose install shrinks by ~19 MB / ~26%. Confirms the project-review doc's
framing (§2 item 2): worth it only if most users are on courses other than Japanese —
still waiting on the learner-mix number from Spencer.
