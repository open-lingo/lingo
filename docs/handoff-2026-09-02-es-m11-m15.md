## Format contract (learned from m10.ir.yaml, use this)

Step kinds: `info, imageMcq, audioWimcq, sim, map, buildLit, listenCompLit,
listenBuildLit, clozeLit, matchLit, speakLit(+cue: recall), textMcq, mcq`.
Shapes:
- `clozeLit` — `es, en, blank, options[], atoms[], why`  (options make it a
  PICK; a 2-option cloze is a coin flip, so it teaches via `why`)
- `buildLit` / `listenBuildLit` — `es, en, atoms[], tiles[]` (`tiles` are the
  DISTRACTOR tiles; answer tiles come from `es`). `buildLit` only: optional
  `also: [..]` — up to 3 vetted alternative orders, each buildable from
  `es`+`tiles` as a multiset (the compiler throws otherwise; grading lane 3
  in `buildAcceptance.ts`, 2026-09-06). Absent = exact grading.
- `audioWimcq` — `target: {surface, emoji}`, `distractors: [{surface, emoji}]`
- `listenCompLit` — `es, en, atoms[], distractorsEn[]`
- `speakLit` — `es, en, atoms: [], cue: recall`
- `matchLit` — `pairs: [{source, target}]`
- `textMcq` — `target, distractors[]`
Checkpoint (L8) is ~20 all-graded steps, "no new words".

Identical brief (`scratchpad/m11-L1-brief.md`), same lesson (m11 L1), rubric
(`scratchpad/rubric.md`) pinned BEFORE any output existed.

|---|---|---|

| tokens | 99.1k | 99.9k |

| steps authored | 21 | 22 |
| **A-gates failed** | 1 (A9) | 1 (A9) |

Decision rule was "Sonnet ships if within 3 B-points with no more A-fails."
Gap is 8. **Opus authors the wave; Sonnet is demoted to QA/verification.**

### The cost finding is the important one
Opus was **18% slower for the same token spend**. The cheaper tier bought
nothing. So the answer to "why does authoring take so long" is NOT the model
tier — a full lesson drafts in ~9 minutes. The remaining cost is the
compile/gate/fix loop and TTS, and the fix for wall-clock is PARALLELISM
(dispatch several lessons at once), not a cheaper model.

### Two bugs the experiment found in MY brief (fix before reusing it)
1. **`pan` and `pero` are already registered** — `pan` in m7 (`m7.ir.yaml:100`),
   `pero` in m6 (`m6.ir.yaml:92`). The brief listed both as m11 pinned atoms.
   They must stay OUT of m11's `newAtoms` (m10 «trabajo» first-write-wins
   precedent) and be re-anchored, not debuted. Opus caught this unprompted and
   was right; Sonnet wrote `el pan` as a debut. `también` IS genuinely new.
2. **The brief contradicted itself**: `leer/correr` were declared
   "INFINITIVE ONLY — never conjugated in m11" while the transfer paragraph
   demanded a step forcing machine application on an undrilled verb. Both
   models resolved it toward the transfer; both therefore emitted untracked
   conjugated forms (Sonnet `leo/lees`, Opus `lee/leo/lees`) — the ONLY A-gate
   failure either scored. Opus flagged the conflict explicitly and contained
   it (`atoms: ["el","libro"]`, no unregistered surface claimed); Sonnet did it
   silently. **Fix: register the transfer cell as a real atom.**

### Where the 8-point B gap came from
- **-ar/-er contrast (B2, 1 vs 3):** Sonnet's contrast step was
  «como» vs «hablo» — both -o forms, so the choice is lexical (eat vs speak)
  and the ENDING is never the variable. Opus staged «Ana ___ en la cocina»
  with `[come, habla]` — same person, the -a/-e ending is the only difference.
  That is the module's whole thesis; Sonnet never tested it.
- **Transfer step (B1, 2 vs 3):** Sonnet's «leo el papel» uses a verb the
  lesson never introduces at all — that is an untaught word, not a transfer.
  Opus debuts `leer` as a bare infinitive, then two steps later demands
  «Ana lee el libro» from a bank holding all three singular cells.
- **Naturalness (B5, 1 vs 3):** «leo el papel» glossed "I read the paper" is
  not Spanish for reading a newspaper (that is «el periódico»); and Sonnet's
  sim shipped a duplicated gloss string ("Do you eat bread? Do you eat bread
  (in general)?") — a copy-paste artifact a learner would see.

   for `multiple_choice`, so its distractors are free). But
   `multiple_choice` is not in `ES_INTRO_TYPES`, so the debut would have

four cells debut legally in place: zero unknownTokens, zero nonIntroDebuts.

### What the agents caught that I had not told them
- **`clozeLit` blanks are matched with `words(es).indexOf(blank)`, no
  punctuation stripping** — so «¿comes pan?» blanking `comes` throws at
  compile (the token is `¿comes`). Two agents found this by READING
  `scripts/draft/es-ir/assemble.mjs` instead of trusting my shape spec.
- **A sim build reply is split on whitespace against the tile bank, so a
  multi-word tile can never appear in a build answer** («todos los días»).
- **No cloze in any shipped ES module is a question** — 178 clozes, zero
  using `¿…?`. An unwritten convention; now written down.
- **`pan` (m7) and `pero` (m6) are already registered.** My brief had both
  as m11 atoms. Caught first in the parity experiment, then again here.

### What only the real gates caught (5 failures, all correct)
1. **pin E2** — a `clozeLit` on «pero» is illegal: past its intro module an
   item is PRODUCED, not picked. Converted to a `buildLit`, same sentence,
   with «y»/«también» in the bank as the two things «pero» is not.
2. **inv 10** — L9's cloze offered «como» as a distractor while the prompt's
   own second half read «pero yo como pan». Kept the sentence, moved the
   contrast to tú-vs-él (`[come, comes]`).
3. **one emoji, one meaning** — 📖 already belongs to «libro» (m3); «leer»

4. **placement bank** — the compiler emits `ES_M{N}_PLACEMENT` only if the IR

5. **inv 24** (caught pre-assembly by my own validator) — L1 spent «¿comes

## m12 «Este, ese» — wave in flight (2026-09-02)

**Spine.** Demonstratives + shopping, deliberately a non-verb breather between
m11's paradigm and m13's gustar. One rule: *a demonstrative takes the gender
and number of the noun it points at.* Spent in a shop, because pointing is
what you actually do there. `aquel/aquella` are NOT taught — two distances
only; the third triples the table for a distinction beginners never need.

**18 atoms, allocated:** L1 este/esta · L2 camisa 👕/falda 👗/zapato 👟 ·
L3 ese/esa · L4 cuánto/cuesta/cuestan · L5 estos/estas/esos/esas ·
L6 caro/barato/comprar · L8 sombrero (transfer only). L7/L9/L10 zero-new.
este/esta and ese/esa are split by an unrelated noun lesson and the plurals
wait until L5 — the interleave doctrine, not an accident of ordering.

**Three decisions worth recording:**

1. **`zapato` is registered singular; «zapatos» rides the m3 plural fold.**
   `moduleBarGuards.ts:138–205` canonicalizes an otherwise-untracked REGULAR
   plural to its singular and an untracked regular feminine of an `-o`
   adjective to its masculine. So `cara/caros/caras/barata/baratos/baratas`
   are free and must NOT be registered — registering them would give each a
   debut requirement it does not need. But **estos/estas/esos/esas ARE
   registered**: este→estos and ese→esos are irregular, so the fold cannot
   reach them.

2. **«esta» vs «está» is taught, not dodged.** `está` (m4, "is somewhere")
   and `esta` (new, "this") differ by one accent and the learner meets them
   in one sentence. The atom registry does not deaccent, so both stay
   trackable; L1 names the pair and one graded step turns on the difference.
   The alternative — silently avoiding `está` for ten lessons — is the
   version that fails on the tester's first real sentence.

3. **The transfer test for a NON-VERB module.** m10 (visitar) and m11
   (recibir) made the learner conjugate a verb the module never drilled. A
   demonstrative module's equivalent is an unseen NOUN whose gender they must
   decide: «sombrero», a loanword into English, so the vocabulary load is
   zero and the whole load falls on the agreement. Pinned shape —
   `buildLit "este sombrero es caro"` with `tiles: ["esta", "esos"]`, a
   wrong-gender and a wrong-number demonstrative, so the answer cannot be
   found by shape. `buildLit` because `build_sentence` is in `ES_INTRO_TYPES`
   and `multiple_choice` is not.

**Three improvements the m11 wave earned, now in the brief:**
- inv 24 is a hard rule (rule 7), not a discovery.
- Agents are told to read `assemble.mjs`'s `throw` statements rather than
  trust my shape spec — three m11 agents found compile-breakers that way.
- pin E2 is named explicitly (an atom from an earlier module must be
  PRODUCED, not picked) — the gate that rejected m11's first draft.
- The `placement:` block is written UP FRONT (`scratchpad/m12-placement.yaml`,
  folded into `assemble-m12.sh`) instead of being discovered missing.

### Two findings the m12 agents surfaced mid-wave

**«son» is a hole in the provenance gate.** It appears in **zero** shipped ES
lessons — verified across every `ir/*.ir.yaml` plus compiled `m1.ts`/`m2.ts` —
yet it sits in `ES_FUNCTION_WORDS` (`moduleBarGuards.ts:80`), so
«estos zapatos son caros» passes every gate with no debut anywhere. The
L7/L8 author refused to spend it uncued in a checkpoint and routed every
plural predicate through `cuestan` instead; that was the right call, and it
means the module was about to ship without the one sentence shape it exists
to produce. Resolution: **L5 debuts «son» deliberately** — one `info` line
(one thing *es*, more than one *son*; «es» has been owned since m6) plus an
intro-capable first contact before any graded use. No registration: it is
closed-class and registering it would collide with `ES_FUNCTION_WORDS`.
L7/L8 and L9/L10 then spend it.

Worth generalising: **`ES_FUNCTION_WORDS` is a licence to *use*, not evidence
the learner has *met* it.** Any future module reaching for a function word
should grep the shipped course first. `están`, `soy`, `eres`, `hay`, `ser`,
`estar` are all on that list and may be in the same state.

**«el libro» had two emoji.** 📖 in m3/m9 (and the registered atom), 📕 in
two m11 image MCQs. Not a gate violation — the "one emoji, one meaning" pin
catches one emoji on two surfaces, not one surface with two emoji — but the
same word showed a different icon in different lessons. Normalised to 📖 and
m11 recompiled; the diff is exactly those two lines.

**Also recorded for the next author:** `esSurfaces` returns nothing for
`word_map`, `dialogue_sim` or `gender_sort`. A debut placed on one of those
is invisible to the provenance gate, and nothing inside a sim counts toward
exposure or production floors. Debut on the step that cashes the word, not
on the map that previews it.

### Brief bug the L3/L4 author caught (my error, not theirs)

My L4 prompt offered «¿cuántos cuestan esos zapatos?» as the model sentence.
Wrong twice over:
- **`cuánto` is invariable with *costar*.** It modifies the verb and there is
  only one price. «¿Cuántos cuestan?» asks *how many cost*, not *how much do
  they cost*. Freezing `cuánto` is also the better lesson — it leaves exactly
  one moving part on screen, which is the point of L4.
- **`esos` is L5's atom.** No plural demonstrative exists in the course at L4.

The author wrote «¿cuánto cuestan los zapatos?» instead, riding m4's articles
and the m3 plural fold for the plural side. Correct on both counts. The
placement bank (`m12-placement.yaml`) already had the invariable form, so
nothing downstream needed changing.

That is the second wave running where **my brief was the weakest artifact and
the agents corrected it from source.** m11: `pan`/`pero` already registered,
and inv 24 missing entirely. m12: this. The pattern is consistent enough to
plan around — brief the *constraints and the reasoning*, and tell the author
to verify the *examples* against the gates rather than copy them.

### «Offered» is not «taught» — a hole no shared gate covers

The L7/L8 author, rebalancing after the «son» rewrite, found that `estas` had
ended up with **zero answer-position slots in L7**: it appeared eight times,
every one of them a distractor tile or a cloze option. `este`, `esa` and
`esos` had exactly one each. The learner was offered them constantly and
never once had to commit to one.

No shared gate catches this. `registerEsAtomUsagePin` counts appearances, and
a distractor is an appearance. So m12 now carries a bespoke pin — **every
pointer earns an answer position**: each of the eight demonstratives must
appear as a `build_sentence`/`listening_build` target, a `speaking` phrase, a
`particle_cloze` correct answer, or an `agreement_cloze` blank answer,
somewhere in the module.

Worth lifting into the shared doctrine pins for every language, not just
here: a word that is only ever a wrong option is decoration. The ES course
has ten modules that have never been checked for it.

The rebalance also paid a pedagogical dividend the author noted: reusing the
map's own noun at a different distance («esta falda» in the map, «esa falda»
four steps later) leaves exactly one variable on screen, which is the version
of the contrast worth drilling.

## m13 «Me gusta, me gustan» — the wave record

Five Opus agents, two lessons each, same protocol as m12. All five returned
green against their own harnesses; the module compiled on the FIRST pass
(`10 lessons, 15 atoms`) and cleared the full ES suite with one defect, which
was mine and not theirs (below).

### The thesis

`gustar` does not mean "to like". It means "to be pleasing", so the thing
liked is the SUBJECT and the verb agrees with *it*, never with the person.
m13 deliberately does **not** teach number agreement as a new idea — m12 just
spent ten lessons on `cuesta`/`cuestan`, which is structurally the same
machine. L9 puts them in one sentence on purpose: «me gustan estos zapatos,
pero cuestan mucho» — two plural verbs, one plural reason.

### The carrier-atom finding (the important one)

Four of the fifteen declared atoms are new SURFACES whose WORDS are already
owned by earlier modules, because `atomModuleBySurfaceWord`
(moduleBarGuards.ts:546) indexes every WORD of every registered surface,
first-write-wins:

| atom    | word-level owner | via          |
|---------|------------------|--------------|
| `me`    | m2               | «me llamo»   |
| `te`    | m2               | «te llamas»  |
| `gusta` | m7               | «me gusta»   |
| `mucho` | m1               | «mucho gusto»|

**This is NOT the m11 `pan`/`pero` mistake and they were deliberately kept.**
`pan`/`pero` were EXACT-surface duplicates — a genuinely duplicated `es:pan`
atom id. Here the ids differ (`es:me` vs `es:me llamo`), so nothing collides.
Registering them IS the module's thesis: m2 and m7 taught «me llamo» and «me
gusta» as unanalysable chunks, and m13's job is to break them open and show
that `me` is a swappable piece and the verb can grow an `-n`.

My first instinct was to drop all four, and it was wrong. Three agents
independently found the collision, reasoned it through, and built around it
correctly before I acted — one of them scanning every `clozeLit` in shipped
m3–m12 and finding **46** already riding the same exemption.

**Consequence for every future author:** a `clozeLit` answered by one of these
reads as a PRIOR-module atom under pin E2 and survives only on the §13.9 law 5
discrimination-trial exemption — EXACTLY TWO options, both taught. A
three-option cloze on any of them fails. This is the normal path, not a hack.
The rule is recorded in the `newAtoms:` header of `ir/m13.ir.yaml`.

### My defect: a semantic pin that did not know m12's own atoms

`THE THESIS: gustan always has a plural subject` failed on
«me gustan estos zapatos, pero cuestan mucho». The sentence is correct;
the pin only recognised `los|las|vacaciones` as plural-subject markers and
had never been taught the plural demonstratives m12 shipped. Fixed by adding
`estos|estas|esos|esas` to both directions of the check, and by making it
collect every violation instead of failing on the first — a fail-fast
semantic pin tells you one sentence, not the shape of the problem.

**The near-miss worth recording.** Grepping `gustan` across the raw compiled
module returns deliberately WRONG Spanish — «sí, me gustan nadar», «¿te gustan
el helado?», «me gustan el zapato». The module MUST print those; they are MCQ
foils the learner has to reject. A pin written over the module blob would have
graded them as if the course taught them. `allSurfaces()` is safe only because
it reads `audioText`/`targetPhrase`/`targetSentence`/`transcript` — answer
positions. **Any semantic pin must grade answer positions, never every string
in the file.** Same doctrine as m12's "every pointer earns an ANSWER position".

### Agent findings worth keeping

- **A cloze option or build tile is an EXPOSURE.** `esSurfaces` pushes
  `options` and `tiles`, so a new atom offered as a foil *before* its
  intro-type debut fails inv 33. L5's first cloze runs `nadar`/`cocinar` only
  for exactly this reason — `viajar` could not be on that board yet.
- **«gustar» may never be printed in a guillemet span.** It is not an m13 atom
  and not in `ES_VERB_ENTRIES`, so an info card naming it would be an
  untracked word. The cards name «gusta» and «gustan» instead — the same
  reason «costar» is absent from m12.
- **«cocina» is a trap for the bespoke test.** It is m4's *kitchen* AND a
  banned conjugation of `cocinar`, so the obvious `/\bcocin(o|as|a)\b/` flags
  m4's legitimate «la cocina». Scope any such regex to the module's own
  surfaces.
- **Pre-existing course defect, not this wave:** 🚪 is bound to both m1's
  «hasta luego» and m3's «puerta». Neither lesson uses it, so nothing is
  visibly wrong today, but the binding is ambiguous.
- No `imageMcq` anywhere in L7–L10: all four m13 nouns are known by then, and
  inv 44 makes English-prompted picture MCQs first-exposure only. Every late
  picture beat is an audio-prompted `audioWimcq`, which is exempt.

### The «son» gate-hole class is now CLOSED — audited, not assumed

Audited across all shipped ES modules by asking, for each word, the module of
FIRST USE against the module where it is first INTRODUCED (named inside an

| word     | first used | first taught | verdict                  |
|----------|-----------|--------------|--------------------------|
| `son`    | m12       | m12          | ok — the m12 wave fixed it |
| `soy`    | m2        | m2           | ok                       |
| `eres`   | m2        | m2           | ok                       |
| `estás`  | m2        | m2           | ok                       |
| `hay`    | m3        | m3           | ok                       |
| `están`  | never     | never        | no exposure              |
| `estar`  | never     | never        | no exposure              |

`ser` flagged initially and is a FALSE POSITIVE: its only occurrence is the

### Audio: the clips were already published

The `esAudioCoverage` ratchet failed with 112 uncovered texts, which looked
like an upload was owed. It was not: AWS SSO had expired, but checking all
158 newly generated clips against
`https://app.openlingoapp.com/tts/v1/es/<hash>.mp3` returned **200 for every
one**. The clips already existed in the bucket from an earlier full-corpus
upload; only the LOCAL corpus was missing them, so `emit_manifest` had
omitted them and the render-side check failed.

**The lesson: an audio-coverage failure is a MANIFEST fact, not an S3 fact.**

concluding anything about publishing. CI never uploads TTS — `deploy.yml:103`
excludes `tts/*` precisely so a deploy cannot delete the corpus.

## m14 «Puedo, quiero» — the wave record

10 lessons, **18 atoms**, thesis: *the stressed vowel breaks (o→ue, e→ie) in
the three singular persons and the third plural, and stays whole in nosotros /
vosotros.* Same five-agent split (L1-L2, L3-L4, L5-L6, L7-L8, L9-L10) against
a header + placement block I wrote.

### The gate failure my brief caused

`m14 unknownTokens: 3 untracked-word occurrences > declared debt 0` — «vuelve»
×2 and «volver» ×1, all in the L8 transfer cell. My brief asserted *"`volver`
is NOT a registered atom"*. That was wrong, and m13's `vacaciones` was already
the counter-precedent sitting in the repo.

**Registration is not teaching.** Registering a surface makes it *legible to
the provenance gate*; whether the learner is drilled on it is decided by the
lesson steps and by bespoke pins, not by the atom list. The fix was to register
`volver`/`vuelve` (no emoji, confined to L8), invert the test pin to assert the
pair is **registered but never drilled**, and exempt `volver` from the
answer-position pin. I found the identical error in the m15 brief and fixed it
before those agents ever read it.

### Three factual errors in my brief that the AGENTS caught, not me

1. **"a `map` also introduces via its revealNote" — FALSE.** `esSurfaces()`
   (`moduleBarGuards.ts:225`) bills nothing for `word_map`, `dialogue_sim` or
   `gender_sort`; they fall through to `default: break`. A map's `audioText` is
   still counted by inv 24, which is a different gate.
2. **inv 24 (`lintSentenceOveruse`) is PER-LESSON, not module-wide** — it runs
   over `lessons.flatMap(...)`, cap >3, min length 8, clozes skipped.
3. **The "no 3+ identical selection runs" rule does not exist in code** —
   `es-quality.test.ts:196` bans runs of **4+**.

A fourth, from the carrier work: the §13.9 law 5 exemption has **no
stem-sharing check**. In code it is exactly
`options.length === 2 && options.every(o => atomModuleBySurfaceWord.has(o)) &&
options[0] !== options[1]`. "Both options share a stem" is pedagogy I should
argue for on its merits, not a gate I can cite.

### The self-check harness was inert (the one that matters)

`$S/vitest-stub.mjs` — the shim agents imported to run doctrine pins outside
vitest — was:

```js
export const describe = () => {};
export const it = () => {};
export const expect = () => ({});
```

`it()` **discards its callback**. No test body ever executed; `expect` was
never even reached. Any wave that reported "doctrine pins pass" through this
stub had run **zero assertions**.

This did **not** reach the shipped modules — m11–m14 were each gated by the
real suite (`npx vitest run src/features/languages/es/`, 965 tests, exit code
read directly). What was hollow was agent *self-reported* confidence. The stub
has been replaced with a working shim that executes bodies, prints failures and
exits 1; it was verified by a deliberately failing case before being trusted.

**The rule: a harness that can only report success has not been tested. Feed
every verifier a known-bad input and watch it fail before believing a pass.**

### The assembler is zsh, not bash

`assemble-m14.sh` declares `#!/bin/zsh` and uses `FILES=(...)` with
`for f in $FILES`. Run under **bash** that expands to the array's FIRST ELEMENT
ONLY, and you get a 2-lesson IR that fails compile with three misleading errors
("expectedLessonCount 10 but carries 2", checkpoint out of range, "must END on
a sim"). Invoke it as `zsh assemble-mNN.sh`.

### Re-assemble before shipping if an agent is still running

The IR was assembled at 17:30:38; the L3-L4 agent rewrote its lesson file at
17:31:22 — 44 seconds later, after it had already reported. The delta was one
English gloss («el sábado y el domingo» → "on Saturday and on Sunday", which is
the correct reading). Harmless here, but it was found only by comparing mtimes
against the assembled IR. **Do that check every wave**: a reporting agent is
not necessarily a finished agent.

### A vacuous pin, found while fixing a typecheck error

`npm run preflight` failed m14 on `TS6133: 'blankOptionSets' is declared but its
value is never read` — a helper collecting every pick-one blank, written and
never called. **`npx vitest run` does not typecheck**, so the ES suite was green
(965 tests) with this sitting in the file. Preflight is the gate that catches
it; that is why it runs before every push.

The lazy fix is to delete the helper. The right one was to ask why it existed.
The carrier pin next to it only walked `particle_cloze`, and a runtime probe
showed the module also has **5 `agreement_cloze` steps carrying 9 blanks**, one
of them (`es-m14-3-l3-agree-yoyella/p1`) answered by the carrier «entiendo» and
therefore facing the very same pin E2 exemption the pin exists to protect. The
helper was the coverage the pin was missing. It is now used, both step types are
checked, and the pin asserts its own non-vacuity:

```ts
expect(blanks.length, "no blanks found — the pin would be vacuous").toBeGreaterThan(0);
expect(carrierBlanks.length, "no carrier-answered blank found — the carrier set is stale").toBeGreaterThan(0);
```

Verified live: 28 `particle_cloze`, 11 carrier-answered, all exactly 2 options;
9 agreement blanks, all 2-option. The pin now makes 12 real assertions.

**Two traps worth naming.** A `for (…) { if (s.type !== X) continue; … }` pin
passes perfectly when nothing has type X — including when the emitter renamed
the type. And grepping the compiled `m14.ts` for `particle_cloze` returns **0**,
because the module calls the `cloze()` helper and the literal lives only in
`grammarHelpers.ts` — absence in source text is not absence at runtime. Probe
the runtime instead; note that the vitest config swallows `console.log`, so
`expect.fail("PROBE …")` is the reliable way to get a count out.

## A shipped defect the m14 wave uncovered: silently dropped atom credit

The L7-L8 author flagged that `resolveAtomIds` (`grammarHelpers.ts:67`) drops a
surface it cannot resolve and says nothing:

```ts
for (const s of surfaces) { const id = resolveAtomId(s); if (id) out.push(id); }
```

No throw, no lint, no gate. So an `atoms:` entry that is not a registered atom
surface costs that step its SRS credit **silently**. The author's point was that
the existing doctrine pin ("exercised atoms resolve to registered `es:` ids") is
structurally unable to fire on IR-authored content, because an unresolvable
surface never becomes a bogus id — it becomes nothing at all.

I audited it across every ES IR file: **3,683 declared surfaces, 12
unresolvable**, all in **m6 and m12** — and all the same class. Every feminine
agreement form was declared as the exercised atom while only the masculine form
is registered:

`bonita  blanca  nueva  mala  pequeña  vieja  buena  roja`

m6 is the gender-agreement module. Steps like `atoms: ["la","casa","es","bonita"]`
credited `la`, `casa` and `es` and threw the adjective away — the module earned
no SRS credit for the very thing it exists to teach, and had shipped that way
for months.

**Fix:** declare the REGISTERED surface. `atoms:` is SRS credit, not display —
it does not have to match the printed text. 31 `atoms:` lines rewritten across
m6 (24) and m12 (7); no printed text touched, so no new TTS and no provenance
movement. Re-audit: **3,683 checked, 0 unresolvable.**

**Gate:** `curriculum/irAtomResolution.test.ts` now walks every `ir/*.ir.yaml`
and fails on any surface that resolves to neither a live atom nor the review
pool. It asserts its own non-vacuity (file count > 0, parsed entries > 1000),
and it was verified by injecting `«zzznotanatom»` into a real IR file and
watching it fail before being trusted.

Two more emitter gaps the same author reported, NOT yet fixed, both worth a
gate when someone is next in this code:
- **`audioWimcq` does not validate that its target surface is a registered
  atom.** A fabricated target reaches the learner and is caught only downstream
  by the provenance bar guard, and only if the word happens to land in
  `esSurfaces`.
- **"buildLit answer word missing from its tile bank" is unplantable** —
  `assemble.mjs` derives the bank from `tileWords(answer)`, so a build can never
  under-specify its own answer. Do not write that gate; it can never fire.

## m15 «Hago, vengo» — the wave record

10 lessons, **19 atoms**, thesis: *a family of verbs whose yo form goes its own
way — and «tengo» was the first one all along.* Registered persons are
deliberately partial: `hacer` yo/tú/él, `venir` and `salir` yo/él, `ver` yo/él,
`tener` infinitive only (m5 already owns tengo/tienes/tiene), plus the
`poner`/`pongo` transfer pair. Mutation scores across the five authors: **39,
40, 43, 48, 60 — zero misses.**

### The error in MY brief, caught by four agents independently

I told all five authors: *"a wrong inflection of a registered infinitive is
licensed in an options/tiles slot — verified against the real gate this wave."*

**That is false, and it was the most dangerous line in the brief.** `esSurfaces`
bills `particle_cloze.options`, `build_sentence`/`listening_build` tiles, and
`match_pairs` sources. A ghost like «haco» is in no atom and no
`ES_VERB_ENTRIES` cell, so in any of those slots it is an untracked word.
Measured by one author against the real gate:

| slot | «haco» (ghost) | «hacemos» (real, unregistered) |
|---|---|---|
| cloze option | FAILS unknownTokens + nonIntroDebuts | FAILS nonIntroDebuts |
| build tile | FAILS unknownTokens | " |
| match source | FAILS unknownTokens | " |
| multiple_choice distractor | passes | passes |
| dialogue_sim option | passes | passes |
| agreement_cloze blank option | passes | passes |

Four of the five authors re-derived this from `esSurfaces` before writing and
designed around it; the fifth never saw a problem because it had put its ghosts
in MCQ distractors anyway. I verified the shipped IR directly: **every one of
the 20 ghost occurrences across all five files sits in a `textMcq`/`mcq`
distractor or a `dialogue_sim` reply.** None in a billed slot.

`m15.test.ts` now pins this structurally rather than trusting it — see the
"ghosts live ONLY in unbilled slots" lane, which walks cloze options, build and
listen-build tiles and match sources, and asserts its own non-vacuity.

### The gate is blind to two of the five verbs

- **`tener.introducedAtModule = 5`** — every `present.*` form folds into PRIOR,
  so «tenemos»/«tienen» pass BOTH real gates.
- **`hacer.introducedAtModule = 16`** — its forms are in
  `getEsRealFormLexicon()` via `ES_VERB_ENTRIES`, so `unknownTokens` can never
  see «hacemos»; it fails only the *debut* half, which any lesson after L2 has
  already satisfied for the hacer family. In the real ten-lesson module a
  «hacemos» in an L9 answer **passes every automated check.**

Only `venir`, `salir`, `ver` and `poner` are genuinely gate-protected — they are
absent from `ES_VERB_ENTRIES` entirely, so a stray «vienes» fails
`unknownTokens` outright. Form discipline for `hacer` and `tener` is a bespoke
lane in `m15.test.ts` and nothing else. **Do not bump `hacer` to ≤14** without
re-reading that pin: it would silently make every hacer form "prior" and
evaporate m15's debut checks.

### Two content corrections the authors made to my spine

1. **"The tú and él forms are completely ordinary" is false.** `venir` →
   «vienes»/«viene» and `tener` → «tienes»/«tiene» carry m14's e→ie stem break.
   Teaching my sentence would have contradicted m14 four lessons later. The info
   cards now scope "ordinary" to the *endings* and name the ie explicitly as a
   link back to m14.
2. **`ver` is a contracted verb, not a regular -er.** Regular -er on stem `v`
   gives *«vee», not «ve». The card now claims only that the ending is the same
   plain -e that «come» and «vive» have worn since m11.

Also corrected: «tengo hambre»/«tengo sed» are **m7's**, not m5's — both the
brief and the header said "since module 5". m5 owns tengo/tienes/tiene and
prints «tengo un perro».

### Process finding: name scratchpad files per-author

Two m15 agents both wrote `$S/mutate-m15.mjs`, and one silently overwrote the
other mid-run. It was caught only because a mutation run printed a foreign
output format. Deliverables were untouched (those had unique names), but any
wave running parallel authors must hand each one a lesson-scoped filename
prefix.

### Repo defect found in passing

`sentenceMcq` (`grammarHelpers.ts:234`) types `distractorsText` as a 3-tuple and
never checks it at runtime. An IR `mcq` with 2 distractors emits an option
`{id:"opt-3", text: undefined}`, and `lintMcqDistractorsCore` then **throws**
`Cannot read properties of undefined (reading 'trim')` instead of reporting a
clean lint failure. Not hit by any shipped lesson, but any author reaching for
`kind: mcq` with two distractors will land on it.
